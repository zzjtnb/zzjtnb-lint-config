# 工程参考

本页说明仓库本身如何组织、检查和发布。它面向维护者，不是业务应用开发指南；公开包的消费方式请从[快速开始](./quick-start)开始。

## 目录边界

```text
zzjtnb-lint-config/
├── docs/                         # 双语 VitePress 文档，Markdown 位于 src/ 源目录
├── internal/                     # 私有工程配置和构建工具
│   ├── lint-configs/             # 私有 ESLint、Stylelint、commitlint、oxfmt、oxlint 配置
│   ├── node-utils/               # Node.js 工具
│   ├── packages/                 # 私有基础、样式和类型包
│   ├── tsconfig/                 # 共享 TypeScript 配置
│   └── vite-config/              # 共享 Vite 配置
├── packages/
│   ├── eslint-config/            # ESLint 公开配置包
│   ├── stylelint-config/         # Stylelint 公开配置包
│   └── markdownlint-config/      # Markdownlint JSONC 共享规则包
├── playground/                   # 单一交互式验证项目
├── scripts/
│   ├── clean.js                  # 将生成物移入系统回收站
│   └── release/index.js          # 唯一发布入口
├── tests/                        # 跨包自动化测试与专用夹具
├── eslint.config.ts              # 仓库 ESLint 入口
├── stylelint.config.ts           # 仓库 Stylelint 入口
├── turbo.json                    # workspace 任务图
└── pnpm-workspace.yaml           # workspace 与 catalog
```

以下三个包属于对外发布范围：

```text
@zzjtnb/eslint-config
@zzjtnb/stylelint-config
@zzjtnb/markdownlint-config
```

根 `packages/` 只存放三个公开配置包；私有基础、样式和类型包集中在 `internal/packages/`。`internal` 和 `playground` 中的 workspace 不属于公开 API。

## 依赖边界

### 公开 ESLint 包

`@zzjtnb/eslint-config`：

- `eslint` 是 peer dependency，由消费项目直接安装；
- `@antfu/eslint-config` 是运行时依赖；
- parser、plugin 和 antfu 规则由上游及本包的依赖边界提供；
- 只提供具名 runtime export `zzjtnb` 和公开类型；
- 不提供 CommonJS 或 default runtime wrapper。

### 公开 Stylelint 包

`@zzjtnb/stylelint-config`：

- `stylelint` 是 peer dependency，由消费项目直接安装；
- PostCSS parser、preset 和 `stylelint-order` 是本包运行时依赖；
- Stylelint 配置使用原生 `Config` 字段；
- `zzjtnb()` 返回对象，default export 是共享默认对象；
- 不要求消费项目复制本包内部 preset 和 plugin 依赖。

### 公开 Markdownlint 包

`@zzjtnb/markdownlint-config` 只发布带注释的 JSONC 规则及中英文说明，没有运行时依赖，也不需要构建或类型生成。消费方使用原生 `extends`，通过本地 CLI2 配置维护扫描范围、自定义规则插件和修复行为。

### 私有包

私有包只服务于当前仓库工程，不应被公开包的 README 当作消费方依赖。新增内部依赖时，应先确认是否真的属于构建、测试或工作区运行时边界。

## 包管理器和 catalog

消费项目如何配置 catalog、迁移分散版本及验证依赖，见 [依赖版本管理教程](./dependencies)。本节只维护本仓库的具体工程约定。

仓库开发环境以根 `package.json` 的 `engines` 和 `packageManager` 为准，不与公开包面向消费方的最低 Node.js 范围混用。使用 `packageManager` 指定的 pnpm 版本，不在文档另行维护版本号。安装前可运行只显示指引的 `node scripts/preinstall.js --help`；该命令不会下载、升级或安装环境。

依赖版本集中在 `pnpm-workspace.yaml` 的 `catalog` 中，包清单中使用：

```json
{
  "devDependencies": {
    "eslint": "catalog:"
  }
}
```

不要在单个 package.json 中重复维护 catalog 已有依赖的具体版本。新增依赖时：

1. 确认它属于哪个包的运行时或开发边界；
2. 先在 workspace catalog 增加版本范围；
3. 在需要它的 package.json 中使用 `catalog:`；
4. 执行 `pnpm install` 更新 lockfile；
5. 运行该包的类型、lint 和构建检查。

## TypeScript 编译与工具 API

仓库通过 catalog 集中维护两项别名：`@typescript/native` 指向 TypeScript 7 编译器并提供 `tsc`；`typescript` 指向微软的 `@typescript/typescript6` 兼容包，为 ESLint、Vue 类型工具和文档示例测试提供编译器 API，并提供 `tsc6`。根类型检查使用 TS7，不把工具 API 版本误认为项目编译版本。

两项别名均列入 `update.ignoreDeps`，升级时一起核对 CLI、编译器 API 消费者、Vue SFC 和声明生成。具体版本只维护在 catalog，不复制到各工作区。安装时若只同步依赖而不执行现有 postinstall/stub，使用 `pnpm install --ignore-scripts`；检查已安装工具使用 `pnpm --config.verifyDepsBeforeRun=error exec`。

## 常用命令

### 安装

```bash
pnpm install
```

安装完成后，根 `postinstall` 会按包执行已声明的 `stub`，生成私有包和工具包所需的本地构建产物。

### 全部 lint

```bash
pnpm lint
```

根 lint 由 Turborepo 调度仓库级 ESLint、Stylelint 和 Markdownlint 任务；其中 ESLint 与 Stylelint 的根任务在 `turbo.json` 中声明了 `^build` 前置依赖，可能构建上游 workspace 包，不是纯源码检查入口。它不等价于公开包发布检查。只允许检查而不允许构建时，使用所属模块维护约定中的直接 CLI。

分别运行：

```bash
pnpm lint:eslint
pnpm lint:stylelint
pnpm lint:markdownlint
```

这些命令不自动修复源码；ESLint 与 Stylelint 会写入各自的检查缓存。根级命令与 workspace 包级任务的调度范围不同，需要执行各 workspace 自己声明的检查时使用 `pnpm lint:workspaces`，或相应的 `lint:workspaces:eslint`、`lint:workspaces:stylelint`、`lint:workspaces:markdownlint`。包级检查可能包含构建前置生命周期，执行前应核对所属包的脚本。

### 格式化

```bash
pnpm format
```

`format` 会调用根 ESLint、Stylelint 和 Markdownlint 的 `--fix` 流程，作用范围是整个仓库。它不是发布脚本的一部分。

如果只需要格式化公开包，应在包目录或通过 filter 执行包级命令：

```bash
pnpm --filter @zzjtnb/eslint-config run format
pnpm --filter @zzjtnb/stylelint-config run format
pnpm --filter @zzjtnb/markdownlint-config run format
```

这三个包当前的包级 `format` 都只执行 ESLint 修复，不等于根级三个工具的完整格式化流程。需要修复公开包 README 等 Markdown 时，另从仓库根执行：

```bash
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc --fix "packages/**/*.md"
```

### 类型检查

```bash
pnpm typecheck
```

需要检查单个区域时，使用对应的 package script：

```bash
pnpm typecheck:root
pnpm --filter @zzjtnb/playground run typecheck
pnpm exec tsc -p internal/packages/types/tsconfig.json --noEmit
```

### 测试

测试统一由根 `vitest.config.ts` 调度，默认使用 Node.js 环境，Vue 组件与状态测试按文件启用 happy-dom，不再通过 Turborepo 转发。测试脚本本身不包含安装或构建；pnpm 的 `verifyDepsBeforeRun` 默认是 `install`，依赖不同步时可能触发既有 `postinstall/stub`。仅检查且不允许安装时，使用 `pnpm --config.verifyDepsBeforeRun=error exec vitest run`，让依赖缺口明确失败，而不是绕过工具的正式入口。

根配置以自身目录固定项目路径，指定该配置时不会因当前工作目录改变测试发现范围；`runner.test.ts` 对比仓库根与测试子目录的发现结果。以下命令均从仓库根执行。

```bash
# 执行全部测试，包括公开包入口检查。
pnpm test

# 执行工作台、脚本、文档配置及包内单元测试。
pnpm test:unit

# 从当前源码验证实际 lint、规则覆盖和自动修复。
pnpm test:integration

# 通过包名验证公开入口与现有构建产物。
pnpm test:packages
```

仓库根级 `tests/` 由根依赖、lint、类型检查和 Vitest 配置统一管理，不是独立 workspace；`integration/` 只存放自动化集成测试，专用输入统一归 `fixtures/`。

- `unit`：覆盖 Playground 状态与引擎、HTTP 契约、脚本和文档配置；各模块测试集中在所属根级 `tests/`，不放在 `src/` 或 `__tests__/`。
- `integration`：`tests/integration/consumer-configs.test.ts` 调用当前源码和真实 lint 引擎；所需输入集中在 `tests/fixtures/`，每份夹具都由测试读取并断言结果。
- `packages`：`tests/integration/package-loading.test.ts` 按包名解析公开导出。ESLint、Stylelint 必须已有与待验证源码对应的构建产物；Markdownlint 直接验证 JSONC 入口，不需要构建。

修改 ESLint 或 Stylelint 源码后，先执行对应包的 `build`，再执行 `test:packages` 或完整 `test`；缺失或陈旧产物不能用源码别名替代，也不能把旧产物通过当作新源码的发布验证。`test:unit` 和 `test:integration` 不依赖这两个公开包的构建产物。

`apps/demo/` 是独立消费配置的示例项目，`playground/` 用于交互演示；两者不代替自动化断言。需要修改输入的测试应在 `.tmp/` 下创建隔离副本，不对版本管理中的夹具直接执行文件写回。

### 构建

```bash
pnpm build
```

常用的局部构建命令：

```bash
pnpm --filter @zzjtnb/docs run build
pnpm --filter @zzjtnb/playground run build
pnpm --filter @zzjtnb/eslint-config run build
pnpm --filter @zzjtnb/stylelint-config run build
```

文档和 Playground 构建会生成本地产物，不应把 `dist`、`.vitepress/dist` 或缓存目录提交到仓库。

## 验证顺序

以下流程包含安装、构建及可能带构建前置步骤的包脚本，适用于已允许执行这些操作的完整验证。仅检查源码时，不要照单执行全流程：使用所属模块维护约定中的直接 CLI，并添加 `--config.verifyDepsBeforeRun=error` 阻止依赖不同步时自动安装。缺少生产产物或浏览器验证时，应明确记录尚未验证的边界。

修改公开配置包后，推荐按以下顺序验证；仅选择实际受影响的包。ESLint、Stylelint 是需要构建和类型检查的两个 TypeScript 包，Markdownlint 直接检查 JSONC，不运行不存在的 build / typecheck。仅修改 Markdownlint 时，先运行其 lint 和源码消费测试；执行全量包入口测试仍要求另两个包有有效产物。

```bash
# 1. 依赖和 workspace 是否一致。
pnpm install

# 2. 两个 TypeScript 配置包的构建和类型检查。
pnpm --filter @zzjtnb/eslint-config run build
pnpm --filter @zzjtnb/eslint-config run typecheck
pnpm --filter @zzjtnb/stylelint-config run build
pnpm --filter @zzjtnb/stylelint-config run typecheck

# 3. 三个公开包的代码 / 配置 lint，以及各包 README 的 Markdown 检查。
pnpm --filter @zzjtnb/eslint-config run lint
pnpm --filter @zzjtnb/stylelint-config run lint
pnpm --filter @zzjtnb/markdownlint-config run lint:eslint
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/**/*.md"

# 4. 执行单元测试、源码消费场景与公开包入口检查。
pnpm test

# 5. 当前 workspace 的交互式集成验证。
pnpm --filter @zzjtnb/playground run lint
pnpm --filter @zzjtnb/playground run typecheck
pnpm --filter @zzjtnb/playground run build

# 6. 文档验证。
pnpm --filter @zzjtnb/docs run lint
pnpm --filter @zzjtnb/docs run build
```

不要用一次根级 lint 失败就判断公开包不可发布。需要先区分：

- 公开包自身错误；
- Playground 集成错误；
- 文档错误；
- 其他 workspace 的既有业务错误。

## 发布范围

根目录只提供一个发布入口：

```bash
pnpm release
```

发布脚本默认发布全部三个公开包，并先询问是否使用默认的统一版本号；也可以自定义统一版本、逐包设置版本，或只发布 ESLint、Stylelint、Markdownlint 中的一个。ESLint 与 Stylelint 检查构建、类型、包内 ESLint 和 Markdown；Markdownlint 是无需构建的 JSONC 配置，只检查包内 ESLint、Markdown 和发布文件。

版本检查、交互升级、打包内容检查及发布行为见[当前发布流程](https://github.com/zzjtnb/zzjtnb-lint-config/blob/main/apps/handbook/当前发布流程.md)；不使用交互脚本时按[原始发布流程](https://github.com/zzjtnb/zzjtnb-lint-config/blob/main/apps/handbook/原始发布流程.md)执行 pnpm 原生命令，npm 官方发布机制与通用错误集中见[发布常见问题](https://github.com/zzjtnb/zzjtnb-lint-config/blob/main/apps/handbook/发布常见问题.md)，脚本与原生命令自身的使用问题留在对应流程。

发布脚本不会自动执行整个 workspace 的 lint、docs 构建、Playground 构建或业务应用检查，也不会自动 commit、tag 或 push。

发布辅助逻辑位于：

```text
scripts/release/index.js
```

发布脚本说明位于：

```text
scripts/release/README.md
```

## 清理生成物

```bash
pnpm clean
```

清理脚本会把以下目录或文件移入系统回收站，而不是物理删除：

```text
.cache
.turbo
coverage
dist
dist.zip
node_modules
.vitepress/cache
```

脚本会跳过：

```text
.git
.idea
.tmp
.vscode
.DS_Store
```

`.tmp/` 内的内容不会被清理。清理需要系统已安装 `trash` 命令；回收失败会报错，不会改为永久删除，已回收内容可从系统回收站恢复。默认保留 `pnpm-lock.yaml`；只有明确需要重新解析依赖时才使用 `pnpm clean --del-lock` 同时回收锁文件。`pnpm clean --help` 只显示帮助，不扫描或移动文件。

执行清理前应确认未运行依赖这些目录的进程；清理后重新执行 `pnpm install`。

## 编辑器协作

`.vscode/settings.json` 是仓库编辑器行为的事实来源，当前原则是：

- 使用 pnpm；
- 关闭 Prettier 和保存时全局格式化；
- ESLint、Stylelint 修复通过 `source.fixAll.*: "explicit"` 显式触发；
- 关闭 VS Code 内置 CSS / SCSS / Less 重复校验；
- `source.organizeImports` 保持 `never`，避免编辑器自行改写 import 顺序；
- Markdownlint 使用 `source.fixAll.markdownlint: "always"`，显式保存与自动保存都会修复；Markdown 手动格式化和粘贴格式化交给 Markdownlint，关闭重复的保存格式化路径。

## 变更后的最小证据

提交或发布前，按实际变更范围保留相应证据，不要求纯文档改动执行所有公开包构建：

- 公开配置包：相关 lint、源码消费测试；两个 TypeScript 包还需类型检查，发布前需构建并验证公开入口。
- Playground：相关状态、组件、引擎与 HTTP 测试及类型检查；交互改动补实际浏览器验证，部署改动补页面构建验证。
- 文档：Markdown 检查、双语本地链接与配置测试；配置和主题改动补类型检查，发布前补站点构建及必要的浏览器验证。
- 工程脚本：对应脚本的自动化测试；带发布、清理等副作用的流程不能仅凭帮助输出或模拟测试宣称真实执行已通过。

依赖已同步时不必重复安装；仅检查且不允许安装时，使用前述 `verifyDepsBeforeRun=error`。安装、构建、服务启动和发布等操作仍按当前授权执行，未执行的必要验证应保留为缺口。

如果某一步因外部服务、网络、既有业务错误或工具超时失败，应在交付说明中明确列出失败命令和原因，不把局部通过写成全部通过。

## 子包命令与根任务的职责

根 `dev`、`build`、`preview` 通过 Turbo 调度同名任务，不维护针对每个应用的转发脚本。仅运行文档站或工作台时，直接选中所属包：

```bash
pnpm --filter @zzjtnb/docs run dev
pnpm --filter @zzjtnb/playground run dev
pnpm --filter @zzjtnb/docs run preview
pnpm --filter @zzjtnb/playground run preview
```

| 应用 | 开发端口 | 预览端口 | 产物 |
| --- | --- | --- | --- |
| 文档站 | 3000 | 3000 | `docs/.vitepress/dist` |
| Playground | 3001 | 3001 | `playground/dist` |

同一应用的 dev 与 preview 不同时运行，因此复用端口；两个应用可以同时运行。端口占用时明确失败，不静默递增，也不在启动脚本中自动杀掉未知进程。

## 文档站源码与主题边界

项目根目录为 `docs/`，通过 `srcDir: 'src'` 指定 `docs/src/` 为正文源目录。中文主题直接放在源目录，英文位于 `src/en/`，静态资源位于 `src/public/`。例如 `src/eslint.md` 对应 `/eslint`，`src/en/eslint.md` 对应 `/en/eslint`；目录分组由侧边栏表达，不添加无必要的 URL 层级。

`.vitepress/config.ts` 维护导航、语言和站点选项；`.vitepress/theme/index.ts` 继承默认主题；样式只覆盖当前需要的品牌变量。扩展默认主题不等于重写导航、搜索和移动端布局，也不意味着自动拥有图片缩放、PWA 或变更记录插件。

### 阅读增强与更新时间

站点使用官方本地搜索、官方 `lastUpdated` 和 `vitepress-plugin-group-icons`。图标插件需要在 Markdown、Vite 和主题 CSS 三处同时接入；代码组用于同一任务的可选写法，不把必须连续执行的步骤藏进互斥页签。

````md
::: code-group

```ts [eslint.config.ts]
// 配置示例
```

:::
````

代码组的标签可包含文件名，图标按标签和语言匹配。插件配置只在站点入口维护，正文使用标准 Markdown 代码组。

`lastUpdated` 读取文件最近一次 Git 提交时间，不是文件保存时间，也不是构建时间。新建且尚未提交的页面可能没有时间；不要填入当前时间伪装成已有历史。CI 拉取代码时保留完整历史，例如 GitHub Actions 的 checkout 使用 `fetch-depth: 0`，避免浅克隆使日期失真。中文和英文页面各自显示各自文件的历史。

PWA、完整提交记录和图片缩放不属于当前站点能力。更新时间不能替代版本发布说明；需要离线阅读或图片放大时，再按实际需求验证缓存更新或图片生命周期，不仅为装饰增加插件。

文档站通过 `pnpm --filter @zzjtnb/docs run typecheck` 检查配置、主题入口及测试类型。正式测试由根 Vitest 的 unit 项目发现 `docs/tests/`，通过 VitePress `resolveConfig` 检查配置，通过 Markdown 渲染检查双语页面、正文锚点、首页资源和导航链接。生产输出仍需独立执行站点构建。

## Turbo 缓存与副作用

构建任务声明真实产物；文档站为 `.vitepress/dist/**`，Playground 为 `dist/**`。`dev` 和 `preview` 是持续运行的服务，关闭任务缓存，不把“启动成功”当作可缓存文件产物。

lint 任务禁用 Turbo 结果缓存与 linter 自身的文件缓存是两件事：前者控制是否跳过任务，后者控制任务执行时是否重复检查文件。排查时同时核对二者，不把远程缓存命中当作新环境下的实际运行证据。

## 从修改到交付的验收矩阵

| 修改范围 | 源码证据 | 运行或产物证据 |
| --- | --- | --- |
| 规则与合并逻辑 | 对应规则测试、类型检查、真实引擎消费 | 发布前验证构建后的包入口 |
| Playground HTTP 接口 | 方法、来源、媒体类型、大小上限与 UTF-8 测试 | 真实页面读取规则和检查文本 |
| 文档正文 | Markdown、链接、锚点、代码示例与中英文对应 | 涉及排版时检查实际页面 |
| 主题与导航 | 正式配置解析和目标页面检查 | 响应式、键盘操作、深浅色和搜索 |
| 发布与清理 | 参数和失败分支测试 | 按授权执行真实流程，记录可恢复状态 |

测试中没有发现错误，不代表没有执行的构建、浏览器交互或外部发布已经通过。先明确所属边界，再选择最小而充分的验证集合。
