# 工程参考

本页说明仓库本身如何组织、检查和发布。它面向维护者，不是业务应用开发指南；公开包的消费方式请从[快速开始](../../docs/src/quick-start.md)开始。

## 目录边界

```text
zzjtnb-lint-config/
├── docs/                         # 中文 VitePress 文档，Markdown 位于 src/ 源目录
├── internal/                     # 仓库工程测试等私有辅助工作区
├── packages/
│   ├── eslint/            # ESLint 公开配置包
│   ├── stylelint/         # Stylelint 公开配置包
│   └── markdownlint/      # Markdownlint JSONC 共享规则包
├── playground/                   # 单一交互式验证项目
├── scripts/
│   ├── clean/                    # 清理脚本及其测试
│   ├── preinstall/               # 安装守卫及其测试
│   ├── ports/                    # 项目端口与清理脚本及其测试
│   └── release/index.js          # 唯一发布入口
├── internal/testing/             # 仓库工程测试工作区
├── eslint.config.js              # 仓库 ESLint 入口
├── stylelint.config.js           # 仓库 Stylelint 入口
├── turbo.jsonc                    # workspace 任务图
└── pnpm-workspace.yaml           # workspace 与 catalog
```

以下三个包属于对外发布范围：

```text
@zzjtnb/eslint-config
@zzjtnb/stylelint-config
@zzjtnb/markdownlint-config
```

根 `packages/` 只存放三个公开配置包；`internal/testing/` 承载仓库工程测试，不作为公开包依赖。Docs、Playground 与手册属于私有项目，不作为 npm API 发布。

## 依赖边界

### 公开 ESLint 包

`@zzjtnb/eslint-config`：

- `eslint` 是 peer dependency，由消费项目直接安装；
- `@antfu/eslint-config` 是运行时依赖；
- parser、plugin 和 antfu 规则由上游及本包的依赖边界提供；
- 只提供具名 runtime export `zzjtnb` 和公开类型；
- 不提供 CommonJS 或 default runtime wrapper。

### 公开 Stylelint 包

`@zzjtnb/stylelint-config`：

- `stylelint` 是 peer dependency，由消费项目直接安装；
- PostCSS parser、preset 和 `stylelint-order` 是本包运行时依赖；
- Stylelint 配置使用原生 `Config` 字段；
- `zzjtnb()` 返回对象，default export 是共享默认对象；
- 不要求消费项目复制本包内部 preset 和 plugin 依赖。

### 公开 Markdownlint 包

`@zzjtnb/markdownlint-config` 的根入口继续提供 JSONC 规则；`/config` 导出带通用忽略的 CLI2 扫描配置，由 src/index.ts 经 tsdown 生成 ESM 与类型。消费方用 .markdownlint-cli2.mjs 复用该入口，再追加项目差异。

### 私有包

私有包只服务于当前仓库工程，不应被公开包的 README 当作消费方依赖。新增内部依赖时，应先确认是否真的属于构建、测试或工作区运行时边界。

## 包管理器和 catalog

消费项目如何配置 catalog、迁移分散版本及验证依赖，见 [依赖版本管理教程](../../docs/src/engineering/versions.md)。本节只维护本仓库的具体工程约定。

编辑器 SDK 使用 docs 已声明的 TS6 经典语言服务；消费示例使用 TS7 原生编译命令；TS7 不提供经典 tsserver。对应路径维护在 .vscode/settings.json，不能把二者的安装目录混用。

仓库开发环境以根 `package.json` 的 `engines` 和 `packageManager` 为准，不与公开包面向消费方的最低 Node.js 范围混用。使用 `packageManager` 指定的 pnpm 版本，不在文档另行维护版本号。安装前可运行只显示指引的 `node scripts/preinstall/index.js --help`；该命令不会下载、升级或安装环境。

依赖版本集中在 `pnpm-workspace.yaml` 的 `catalog` 中，包清单中使用：

```json
{
  "devDependencies": {
    "eslint": "catalog:"
  }
}
```

不要在单个 package.json 中重复维护 catalog 已有依赖的具体版本。新增依赖时：

1. 确认它属于哪个包的运行时或开发边界；
2. 先在 workspace catalog 增加版本范围；
3. 在需要它的 package.json 中使用 `catalog:`；
4. 执行 `pnpm install` 更新 lockfile；
5. 运行该包的类型、lint 和构建检查。

## TS 源码导入

三个包使用 TypeScript 的 bundler 模块解析，由 tsdown 构建。包内相对导入优先省略后缀，例如 `./factory`；确需后缀时必须对应真实文件，不能用不存在的 `.js` 指向 `.ts`。

TypeScript 支持后缀替换，因此 `.js` 指向 `.ts` 不一定产生编译错误。包源码按上述导入约定维护，Node 插件与规则沿用 antfu 默认，不额外启用模块存在性检查。真实 JS、JSON 资源和 dist 中的 MJS 产物保留实际后缀。

## TypeScript 编译与工具 API

默认 catalog 为消费示例提供 TS7；需要经典编译器 API 的工具通过 `catalog:typescript6` 声明 TS6，Playground 同样引用 TS6 命名目录，不再维护相同编译器的另一份范围。Stylelint、Markdownlint 的构建、类型检查和测试统一使用模板的正式 TS7；JSONC 规则通过专用解析器读取，不依赖 TS6 API。ESLint 的 typescript-eslint 尚不支持 TS7，运行时保留 TS6，声明使用 tsdown 的 tsc 后端，不另装预览版编译器。

TS7 构建提示：tsdown 0.23.3 使用的 rolldown-plugin-dts 0.28.8 在启用 tsgo 生成器时固定输出实验性 API 警告，即使已安装正式 TypeScript 7.0.2 也会出现。它不表示声明生成失败；应按构建退出状态、类型检查和消费测试确认结果。当前稳定版没有关闭此单条提示的正式选项，保持工具链与提示原样，后续升级构建插件时复核，不通过降级编译器或过滤全部警告处理。

升级时分别核对 CLI、经典编译器 API、Vue SFC 和声明生成。具体版本只维护在 catalog，不复制到各工作区。安装时若只同步依赖而不执行 postinstall/build，使用 `pnpm install --ignore-scripts`；检查已安装工具使用 `pnpm --config.verifyDepsBeforeRun=error exec`。

### 包清单字段说明

package.json 必须保持严格 JSON，不插入注释；通用字段在此说明。依赖版本只在 pnpm-workspace.yaml 的 catalog 中维护，各目录旁的注释解释依赖用途，包清单通过 catalog: 引用；workspace: 只引用本仓库工作区，不用于注册表第三方包。

| 字段 | 用途与生效条件 |
| --- | --- |
| name / version | 包的公开标识和当前版本；应用也使用 name 参与工作区筛选。 |
| private | true 禁止发布到注册表；公开配置包不启用。 |
| type | module 将 .js 按 ESM 解释；不改变 .mjs 或 .cjs 的显式语义。 |
| description / keywords | 发布页的说明与检索标签，不改变检查规则。 |
| author / license | 作者与许可证声明；必须与实际分发许可一致。 |
| homepage / repository / bugs | 项目主页、源码位置和问题反馈入口。repository.directory 定位 monorepo 内的所属包。 |
| packageManager | 固定仓库使用的 pnpm 版本，供环境设置和安装守卫读取。 |
| engines.node / engines.pnpm | 声明所属项目可用的运行时范围；公开包与工程环境分别维护，不混用。 |
| exports | 明确可供外部导入的入口；tsdown 包由 exports: true 根据实际产物维护。 |
| main | 为支持该字段的消费工具提供默认文件入口；不能代替 exports 的子路径契约。 |
| files | npm 打包的允许文件；实际内容仍需用 pack --dry-run 预览。 |
| publishConfig.access | public 允许公开发布作用域包；不等于已经上传。 |
| dependencies | 所属工作区运行或构建实际需要的直接依赖，传递依赖不作为直接 API 使用。 |
| devDependencies | 开发、测试、类型检查及构建工具；按实际消费方声明。 |
| peerDependencies | 公开配置包要求消费方提供的兼容检查引擎范围。 |
| scripts | 显式命令入口；没有声明的名字不能通过 pnpm run 调用。root 与包内同名入口按当前目录分别执行。 |
| scripts.bootstrap / preinstall / postinstall | 安装入口、版本守卫和公开包本地产物准备；postinstall 不构建文档站或工作台应用。 |
| scripts.build / dev / preview | 生产构建、监听开发和已有产物预览；工具及端口由所属配置决定。 |
| scripts.generate / build-only | 工作台资源生成与只运行 Vite 的构建入口；build-only 要求资源已生成。 |
| scripts.typecheck | 仅检查类型；根入口通过 Turbo 汇总各 TypeScript 工作区。 |
| scripts.lint / lint:* | 只报告对应范围的问题；根入口聚合三个工具，消费示例保留自己的配置。 |
| scripts.format / format:* | 复用检查入口并追加 --fix，会写回规则可修复的内容。 |
| scripts.test / test:unit / test:e2e | 所属运行器的测试入口；Vitest 单次执行追加 --run，Playwright 单独执行，不与单测混用。 |
| scripts.release | 根入口是交互发布流程；三个 tsdown 包内为 bumpp 版本管理，含 Git 副作用，不能混用。 |
| scripts.prepublishOnly | 发布前重建公开包，保证 npm 使用当前源码的产物；Markdownlint 同样需要构建扫描入口。 |
| scripts.predev / ports | 根 dev 前清理项目监听端口；ports 可显式输入多个端口，详见所属脚本说明。 |
| scripts.clean | 根清理工具入口，真实执行会回收匹配生成物，测试不会调用真实清理。 |
| scripts.lint:tui | 以 Turbo 终端界面展示相同检查任务，不新增另一套规则。 |

## 常用命令

### 安装

```bash
# 同步当前工作区依赖与锁文件，并执行已配置的安装生命周期。
pnpm install
```

安装完成后，根 `postinstall` 会按包执行已声明的 `build`，仅生成 packages 下公开配置包的本地构建产物，不构建 Docs 和 Playground。

### tsdown 包脚本

三个公开包沿用 tsdown 模板入口：build 使用 tsdown 生成发布产物，dev 以 --watch 持续构建，test 启动 Vitest 交互模式，typecheck 使用 tsc --noEmit 检查类型，prepublishOnly 在发布前重新构建。Vitest 单次执行使用 test --run，CI 默认关闭监听；Playground 保留脚手架的 test:unit --run。Markdownlint 的 JSONC 规则原样发布，扫描入口使用相同 tsdown 构建。

包内 release 使用 bumpp 交互管理版本，默认启用提交、打标签和推送，不等于上传 npm；仅在明确需要这些 Git 操作时执行。仓库统一发布仍使用根 pnpm release，沿用已有检查和恢复流程。包级 version:*和 release:* 保留各自独立职责。

### 全部 lint

```bash
# 运行当前项目已配置的代码、样式和文档检查，不自动修复。
pnpm lint
```

根 lint 由 Turborepo 调度仓库级 ESLint、Stylelint 和 Markdownlint 任务；三个工具的根任务在 `turbo.jsonc` 中均声明了 `^build` 前置依赖，可能构建上游 workspace 包，不是纯源码检查入口。它不等价于公开包发布检查。只允许检查而不允许构建时，使用所属模块维护约定中的直接 CLI。

分别运行：

```bash
# 仅运行 ESLint 检查，不自动修复文件。
pnpm lint:eslint
# 仅运行 Stylelint 检查，不自动修复文件。
pnpm lint:stylelint
# 仅运行 Markdownlint 检查，不自动修复文件。
pnpm lint:markdownlint
```

这些命令不自动修复源码；ESLint 与 Stylelint 会写入各自的检查缓存。Docs、Playground 和 apps/handbook 不再维护独立检查配置或脚本，统一从根目录执行。apps/demo 是独立消费示例，保留演示用配置与检查命令。

### 格式化

```bash
# 按当前项目配置自动修复代码、样式与文档，会写回文件。
pnpm format
```

`format` 会调用根 ESLint、Stylelint 和 Markdownlint 的 `--fix` 流程，作用范围是整个仓库。它不是发布脚本的一部分。

三个公开包不维护 `lint`、`lint:*` 或 `format` 脚本；检查与格式化统一从根目录运行，缓存参数也只在根检查入口维护。需要修复公开包 README 等 Markdown 时，另从仓库根执行：

```bash
# 检查并自动修复指定 Markdown 文件，使用命令中的配置或 CLI2 自动发现配置。
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.mjs --fix "packages/**/*.md"
```

### 类型检查

```bash
# 检查当前项目的 TypeScript 类型，不输出编译产物。
pnpm typecheck
```

根命令通过 Turbo 运行各 TypeScript 工作区的 typecheck，不维护根 tsconfig。每个包含 tsconfig.json 的包都声明独立入口和对应编译器依赖，避免根检查遗漏。

需要检查单个区域时，使用对应的 package script：

```bash
# 检查当前项目的 TypeScript 类型，不输出编译产物。
pnpm typecheck
# 检查工作台的 TypeScript 类型，不输出编译产物。
pnpm --filter @zzjtnb/playground run typecheck
# 检查文档站的 TypeScript 类型，不输出编译产物。
pnpm --filter @zzjtnb/docs run typecheck
```

### 测试

测试按职责归各工作区，根目录不维护 Vitest 配置或 tests 目录。根命令按工作区顺序汇总 test，避免独立 Vitest 进程同时清理共享模块缓存，并运行 Playground 脚手架的 test:unit --run，不执行安装、构建或浏览器 E2E。Vitest 在 CI 和非交互终端单次运行；本地交互模式需明确单次运行时追加 --run。

```bash
# 顺序运行各工作区测试及工作台单元测试，不启动浏览器 E2E。
pnpm test
# 运行 ESLint 配置包的单元及契约测试，完成一次后退出。
pnpm --filter @zzjtnb/eslint-config run test --run
# 运行 Stylelint 配置包的单元及契约测试，完成一次后退出。
pnpm --filter @zzjtnb/stylelint-config run test --run
# 运行 Markdownlint 配置包的单元及契约测试，完成一次后退出。
pnpm --filter @zzjtnb/markdownlint-config run test --run
# 运行文档站的单元及契约测试，完成一次后退出。
pnpm --filter @zzjtnb/docs run test --run
# 运行工作台的单元及契约测试，完成一次后退出。
pnpm --filter @zzjtnb/playground run test:unit --run
# 运行工程脚本的单元及契约测试；交互终端下 Vitest 默认监听变化。
pnpm --filter @zzjtnb/scripts run test
# 运行仓库工程契约的单元及契约测试；交互终端下 Vitest 默认监听变化。
pnpm --filter @zzjtnb/testing run test
```

- 三个公开包：测试、夹具与辅助函数归各包 tests，使用 Vitest。入口测试按包名加载现有产物；ESLint、Stylelint 源码变更后先运行各自 build，不用源码别名替代发布验证。
- Playground：沿用 Vue 脚手架的 Vitest/jsdom 和 src/__tests__；Playwright E2E 归 e2e，单独执行 test:e2e。
- Docs 和消费示例：使用自身的 Vitest 和 tests。
- scripts：只保留安装守卫、清理和发布脚本自身的测试，使用 node:test。模块 mock 所需的实验开关由所属命令声明，不执行真实清理或发布。
- internal/testing：仓库工作区契约、工具链、生成物忽略范围和测试发现验证，使用 node:test；不作为公开包的依赖。

仅使用已安装工具时添加 --config.verifyDepsBeforeRun=error，避免 pnpm 默认的依赖同步触发安装生命周期。自动化测试通过不能替代生产构建、独立安装或浏览器验收。

### 构建

```bash
# 构建当前项目的生产产物。
pnpm build
```

常用的局部构建命令：

```bash
# 构建文档站的生产产物。
pnpm --filter @zzjtnb/docs run build
# 构建工作台的生产产物。
pnpm --filter @zzjtnb/playground run build
# 构建 ESLint 配置包的生产产物。
pnpm --filter @zzjtnb/eslint-config run build
# 构建 Stylelint 配置包的生产产物。
pnpm --filter @zzjtnb/stylelint-config run build
```

文档和 Playground 构建会生成本地产物，不应把 `dist`、`.vitepress/dist` 或缓存目录提交到仓库。

## 验证顺序

以下流程包含安装、构建及可能带构建前置步骤的包脚本，适用于已允许执行这些操作的完整验证。仅检查源码时，不要照单执行全流程：使用所属模块维护约定中的直接 CLI，并添加 `--config.verifyDepsBeforeRun=error` 阻止依赖不同步时自动安装。缺少生产产物或浏览器验证时，应明确记录尚未验证的边界。

修改公开配置包后，推荐按以下顺序验证；仅选择实际受影响的包。三个公开包均先构建并执行类型检查，再验证源码及公开入口；Markdownlint 同时保留原始 JSONC 规则文件。

```bash
# 1. 依赖和 workspace 是否一致。
pnpm install

# 2. 三个 TypeScript 配置包的构建和类型检查。
pnpm --filter @zzjtnb/eslint-config run build
# 检查 ESLint 配置包的 TypeScript 类型，不输出编译产物。
pnpm --filter @zzjtnb/eslint-config run typecheck
# 构建 Stylelint 配置包的生产产物。
pnpm --filter @zzjtnb/stylelint-config run build
# 检查 Stylelint 配置包的 TypeScript 类型，不输出编译产物。
pnpm --filter @zzjtnb/stylelint-config run typecheck
# 构建 Markdownlint 扫描入口及声明。
pnpm --filter @zzjtnb/markdownlint-config run build
# 检查 Markdownlint 源码、测试与构建配置类型。
pnpm --filter @zzjtnb/markdownlint-config run typecheck

# 3. 仓库共用检查入口，同时覆盖公开包、工作台、文档和脚本。
pnpm lint

# 4. 执行单元测试、源码消费场景与公开包入口检查。
pnpm test

# 5. 当前 workspace 的交互式集成验证。
pnpm --filter @zzjtnb/playground run typecheck
# 构建工作台的生产产物。
pnpm --filter @zzjtnb/playground run build

# 6. 文档验证。
pnpm --filter @zzjtnb/docs run build
```

不要用一次根级 lint 失败就判断公开包不可发布。需要先区分：

- 公开包自身错误；
- Playground 集成错误；
- 文档错误；
- 其他 workspace 的既有业务错误。

## 发布范围

根目录只提供一个发布入口：

```bash
# 启动仓库交互发布流程，逐步确认范围、版本、检查与上传。
pnpm release
```

发布脚本默认发布全部三个公开包，并先询问是否使用默认的统一版本号；也可以自定义统一版本、逐包设置版本，或只发布 ESLint、Stylelint、Markdownlint 中的一个。所选包分别执行构建、类型检查与单次测试，随后调用一次根目录 lint 检查整个仓库，最后核对发布文件。

版本检查、交互升级、打包内容检查及发布行为见[当前发布流程](https://github.com/zzjtnb/zzjtnb-lint-config/blob/main/apps/handbook/当前发布流程.md)；不使用交互脚本时按[原始发布流程](https://github.com/zzjtnb/zzjtnb-lint-config/blob/main/apps/handbook/原始发布流程.md)执行 pnpm 原生命令，npm 官方发布机制与通用错误集中见[发布常见问题](https://github.com/zzjtnb/zzjtnb-lint-config/blob/main/apps/handbook/发布常见问题.md)，脚本与原生命令自身的使用问题留在对应流程。

发布脚本不会自动执行整个 workspace 的 lint、docs 构建、Playground 构建或业务应用检查，也不会自动 commit、tag 或 push。

发布辅助逻辑位于：

```text
scripts/release/index.js
```

发布脚本说明位于：

```text
scripts/release/README.md
```

## 清理生成物

```bash
# 运行仓库清理脚本，回收其规则匹配的生成物和空目录。
pnpm clean
```

清理脚本会把以下目录或文件移入系统回收站，而不是物理删除：

```text
.cache
.turbo
coverage
dist
dist.zip
node_modules
.vitepress/cache
```

脚本会跳过：

```text
.git
.idea
.tmp
.vscode
.DS_Store
```

扫描时提示隐藏内容，以上跳过目录不会被遍历。生成物回收后，自底向上回收真正的空目录；只有 `.gitkeep` 的约定目录保留，已有其他内容时自动回收多余的 `.gitkeep`，仓库根目录始终保留。

`.tmp/` 内的内容不会被清理。清理需要系统已安装 `trash` 命令；回收失败会报错，不会改为永久删除，已回收内容可从系统回收站恢复。默认保留 `pnpm-lock.yaml`；只有明确需要重新解析依赖时才使用 `pnpm clean --del-lock` 同时回收锁文件。`pnpm clean --help` 只显示帮助，不扫描或移动文件。

执行清理前应确认未运行依赖这些目录的进程；清理后重新执行 `pnpm install`。

## 编辑器协作

`.vscode/settings.json` 是仓库编辑器行为的事实来源，当前原则是：

- 使用 pnpm；
- 关闭 Prettier 和保存时全局格式化；
- ESLint、Stylelint 修复通过 `source.fixAll.*: "explicit"` 显式触发；
- 关闭 VS Code 内置 CSS / SCSS / Less 重复校验；
- `source.organizeImports` 保持 `never`，避免编辑器自行改写 import 顺序；
- Markdownlint 使用 `source.fixAll.markdownlint: "always"`，显式保存与自动保存都会修复；Markdown 手动格式化和粘贴格式化交给 Markdownlint，关闭重复的保存格式化路径。

## 变更后的最小证据

提交或发布前，按实际变更范围保留相应证据，不要求纯文档改动执行所有公开包构建：

- 公开配置包：相关 lint、源码消费测试；三个 TypeScript 包还需类型检查，发布前需构建并验证公开入口。
- Playground：相关状态、组件、真实引擎与沙箱协议测试及类型检查；交互改动补实际浏览器验证，部署改动补页面构建验证。
- 文档：Markdown 检查、中文页面链接与配置测试；配置和主题改动补类型检查，发布前补站点构建及必要的浏览器验证。
- 工程脚本：对应脚本的自动化测试；带发布、清理等副作用的流程不能仅凭帮助输出或模拟测试宣称真实执行已通过。

依赖已同步时不必重复安装；仅检查且不允许安装时，使用前述 `verifyDepsBeforeRun=error`。安装、构建、服务启动和发布等操作仍按当前授权执行，未执行的必要验证应保留为缺口。

如果某一步因外部服务、网络、既有业务错误或工具超时失败，应在交付说明中明确列出失败命令和原因，不把局部通过写成全部通过。

## 子包命令与根任务的职责

根 `dev`、`build`、`preview` 通过 Turbo 调度同名任务，不维护针对每个应用的转发脚本。仅运行文档站或工作台时，直接选中所属包：

```bash
# 启动文档站开发服务并监听源码变化。
pnpm --filter @zzjtnb/docs run dev
# 启动工作台开发服务并监听源码变化。
pnpm --filter @zzjtnb/playground run dev
# 启动文档站已有生产产物的本地预览服务。
pnpm --filter @zzjtnb/docs run preview
# 启动工作台已有生产产物的本地预览服务。
pnpm --filter @zzjtnb/playground run preview
```

| 应用 | 开发端口 | 预览端口 | 产物 |
| --- | --- | --- | --- |
| 文档站 | 3000 | 4173 | `docs/.vitepress/dist` |
| Playground | 3001 | 3001 | `playground/dist` |

Docs 的开发端口由自身 `.env` 配置，预览使用 VitePress 默认 4173，可通过 `--port` 指定。Playground 的开发与预览使用其自身 `.env` 中的同一端口，不同时运行。端口占用时明确失败，不静默递增，也不在启动脚本中自动杀掉未知进程。

## 文档站源码与主题边界

项目根目录为 `docs/`，通过 `srcDir: 'src'` 指定 `docs/src/` 为正文源目录。本站只提供中文站点，正文直接放在源目录，静态资源位于 `src/public/`。例如 `src/eslint/index.md` 经官方 rewrites 对应 `/eslint`，详细页按包目录组织；公开包另有中英文 README，不代表站点存在英文路由。目录分组由侧边栏表达，不添加无必要的 URL 层级。

`.vitepress/config.ts` 维护导航、语言和站点选项；`.vitepress/theme/index.ts` 继承默认主题；样式只覆盖当前需要的品牌变量。扩展默认主题不等于重写导航、搜索和移动端布局，也不意味着自动拥有图片缩放、PWA 或变更记录插件。

### 阅读增强与更新时间

站点使用官方本地搜索、官方 `lastUpdated` 和 `vitepress-plugin-group-icons`。图标插件需要在 Markdown、Vite 和主题 CSS 三处同时接入；代码组用于同一任务的可选写法，不把必须连续执行的步骤藏进互斥页签。

````md
::: code-group

```js [eslint.config.js]
// 配置示例
```

:::
````

代码组的标签可包含文件名，图标按标签和语言匹配。插件配置只在站点入口维护，正文使用标准 Markdown 代码组。

`lastUpdated` 读取文件最近一次 Git 提交时间，不是文件保存时间，也不是构建时间。新建且尚未提交的页面可能没有时间；不要填入当前时间伪装成已有历史。CI 拉取代码时保留完整历史，例如 GitHub Actions 的 checkout 使用 `fetch-depth: 0`，避免浅克隆使日期失真。每个页面显示自身源文件的 Git 历史。

PWA、完整提交记录和图片缩放不属于当前站点能力。更新时间不能替代版本发布说明；需要离线阅读或图片放大时，再按实际需求验证缓存更新或图片生命周期，不仅为装饰增加插件。

文档站通过 `pnpm --filter @zzjtnb/docs run typecheck` 检查配置、主题入口及测试类型。正式测试由文档工作区自己的 Vitest 发现 `tests/`，通过 VitePress `resolveConfig` 检查配置，通过 Markdown 渲染检查中文页面、正文锚点、首页资源和导航链接。生产输出仍需独立执行站点构建。

## Turbo 缓存与副作用

根配置使用 turbo.jsonc 维护注释。`//#lint:eslint` 等名称是 Turbo [官方根任务语法](https://turborepo.dev/docs/crafting-your-repository/configuring-tasks#registering-root-tasks)，对应根 package.json 的检查脚本，不是自定义插件；JSONC、任务输入和环境变量见[官方配置参考](https://turborepo.dev/docs/reference/configuration)。

构建任务声明真实产物；文档站为 `.vitepress/dist/**`，Playground 为 `dist/**`。根 `dev` 先通过 pnpm 默认的 `predev` 钩子清理项目端口，再启动 Turbo；应用分别在自身 `.env` 中维护 `VITE_PORT`，端口清理脚本的 config.ts 只维护清理目标，不供应用导入。指定其他端口与终止行为见[端口脚本](../../scripts/ports/README.md)。`dev` 和 `preview` 是持续运行的服务，关闭任务缓存，不把“启动成功”当作可缓存文件产物。

lint 任务禁用 Turbo 结果缓存与 linter 自身的文件缓存是两件事：前者控制是否跳过任务，后者控制任务执行时是否重复检查文件。排查时同时核对二者，不把远程缓存命中当作新环境下的实际运行证据。

## catalog 与工具链维护

版本集中在同一个根 `pnpm-workspace.yaml`,不代表所有消费者必须使用同一个版本.pnpm 官方支持默认目录与多个命名目录并存,用于不同兼容线或分阶段迁移.

```yaml [pnpm-workspace.yaml]
# catalog: 和 catalog:default 均引用默认目录.
catalog:
  # 默认 TypeScript 编译器的版本范围；消费方通过 catalog: 引用，不在各包重复版本号。
  typescript: ^7.0.2
# 为确有不同兼容要求的消费者提供命名版本范围，其他依赖使用默认 catalog。
catalogs:
  # docs,测试和经典 API 消费工具共用.
  typescript6:
    # TS6 兼容范围；消费方通过 catalog:typescript6 引用，不回退到默认 TS7 目录。
    typescript: ^6.0.3
```

| 消费者 | package.json 中的声明 | 版本来源 |
| --- | --- | --- |
| 消费示例 apps/demo | `"typescript": "catalog:"` | 默认目录，TS7 CLI 兼容线 |
| docs,internal/testing,经典 API 工具 | `"typescript": "catalog:typescript6"` | TypeScript 6 共用兼容范围 |
| playground | `"typescript": "catalog:typescript6"` | 与其他工具共用 TS6 兼容范围 |

本表仅说明本仓库内部工作区,不要求公开包消费项目采用相同目录名称或 TypeScript 范围.本仓库不使用 `@typescript/native`,也不把默认 catalog 改回 TS6.工具需要经典 API 时,由真正消费 API 的包直接声明依赖;普通 TS6 已能满足需求时,不另外维护同义别名.

### 两个字段是否必须同时存在?

不必须.`catalog` 是默认目录的声明简写;官方也支持在单个顶层 `catalogs` 下使用 `default` 声明默认目录.两种布局都由同一份根清单维护,消费者的 `catalog:` 引用不变.本仓库保留 `catalog` 加 `catalogs` 的布局,不在 `catalog` 和 `catalogs.default` 重复保存相同条目.

`catalog:` 是 `catalog:default` 的简写;`catalog:typescript6` 只能读取 `catalogs.typescript6`,不能回退到默认目录.不同版本不能共用同一个目录内的同名条目,但可以在同一个工作区清单中集中管理.相同兼容范围尽量共用命名目录,不按应用复制完全相同的版本表.

### 兼容编译器的批量升级保护

命名 catalog 不是版本上限。`pnpm up -L -r` 会忽略已有范围，可能把 TS6 改成 TS7。当前仓库使用 pnpm 正式的 [update.ignoreDeps](https://pnpm.io/settings/dependency-resolution#updateignoredeps) 排除兼容敏感依赖：

```yaml [pnpm-workspace.yaml]
# TypeScript 编译器与声明生成 API 必须单独核对兼容性，不随全量 latest 升级。
update:
  # 按依赖名生效，覆盖默认和命名 catalog；不只针对 TS6 目录。
  ignoreDeps:
    - typescript
```

这会同时保护 TS6 和默认 TS7 CLI；其他依赖仍可正常批量升级。需要更新编译器时，先人工修改根 catalog 的对应范围，再执行安装、类型检查、三个包的消费测试与构建，不通过全量 latest 猜测工具 API 兼容性。

```bash
# 批量升级其他工作区依赖；上面列出的编译器依赖保持原声明。
pnpm up -L -r
# 人工确认并修改编译器范围后，同步安装与锁文件；此命令不是 latest 升级。
pnpm install
```

`updateConfig.ignoreDependencies` 是旧名称；本仓库只使用当前正式字段，不并存两套设置。

### 格式化,安装和升级分别负责什么?

- `pnpm/json-enforce-catalog` 沿用官方默认行为：检查 dependencies、devDependencies，autofix 默认 true，相同版本可复用 catalog；范围冲突时默认创建命名 catalog 保留原范围。conflicts_* 是插件生成的目录名称，本身不是错误。只有确有重复或无引用时，才由对应 YAML 规则报错。不要用 conflicts: overrides 强行统一未知兼容范围。
- `pnpm/yaml-no-duplicate-catalog-item` 配置为 `checkDuplicates: exact-version`,允许同名包声明不同范围,仍报告同名同范围重复.它比较声明,不保证不同范围一定解析出不同版本.
- `pnpm/yaml-enforce-settings` 只移除 trustPolicy 强制值；其他上游设置保持原样.
- catalog 记录版本范围,锁文件记录实际解析结果.使用 `pnpm install --frozen-lockfile` 校验清单和锁文件一致,不能把 catalog 当成不可变版本锁.

根目录普通 `pnpm up -L`、递归 `pnpm up -r -L`、过滤指定包或进入子目录升级的作用范围不同。升级前先确定消费者范围，分别核对默认与命名 catalog 的版本差异，不把独立命名当成禁止升级的保证。

日常升级应先选择消费者与兼容线,再核对工作区清单,包清单和锁文件差异,并验证受影响的类型检查,工具加载和构建.要保留脚手架范围,就不对该范围执行无约束的跨主版本升级.当前 `update.ignoreDeps` 同时保护默认与命名目录的 TypeScript；升级编译器时单独修改对应范围并验证，不通过全量 latest 绕过兼容范围。

### 配置加载与编译器职责

仓库的 ESLint 与 Stylelint 入口分别使用 `eslint.config.js`、`stylelint.config.js`，根 `package.json` 已声明 `"type": "module"`。直接由 Node.js 加载 ESM，不需要 TS 配置加载器、额外 flag 或 Stylelint 的编译器 packageExtensions。

公开 ESLint 包保留 typescript-eslint 当前需要的 TS6 运行时 API；它不决定消费项目的编译器版本。Stylelint、Markdownlint 的构建与测试使用模板的正式 TS7。Playground 的 generate 脚本直接执行 jiti CLI，因此 jiti 只由该实际消费者自行声明，不作为 ESLint 公开包的运行依赖。

构建元数据插件按默认与命名 catalog 分别解析，展示声明范围，不把 `catalog:typescript6` 显示为默认 TS7，也不把声明范围当作锁文件的解析版本。pnpm 打包时展开 catalog 引用，消费方不需要配置仓库的 catalog。

官方依据：[Catalogs](https://pnpm.io/catalogs)、[update](https://pnpm.io/cli/update)。具体行为以根 `packageManager` 指定版本为准。
