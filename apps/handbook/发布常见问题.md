# 发布常见问题

本页集中整理 npm 官方发布机制及通用错误：账号与权限、registry、版本占用、分发标签、OTP / 2FA、取消发布和远程结果核验。以下问题不因使用本项目脚本或直接执行命令而改变。

本项目交互脚本自身的限制、提示和失败恢复归[当前发布流程][current]；pnpm 原生命令的使用方式、目录和构建问题归[原始发布流程][commands]，不混入本页。

除特别说明，命令从仓库根目录执行。涉及登录、安装、版本写入、publish、dist-tag、deprecate 或 unpublish 的命令都有副作用，应在确认目标和权限后主动执行；不要把排障示例整段批量运行。

## 发布失败：401 / 403 / 404 PUT

### 如何判断

- `401 Unauthorized` 常与认证失效有关。
- `403 Forbidden` 还可能涉及包 / scope 权限、2FA 或账号发布策略。
- `404 Not Found - PUT ...` 发生在写入阶段时，不等同于“包不存在”；需先核对账号、权限、包名与 registry。
- 已登录只证明当前身份可被识别，不证明该身份拥有目标包发布权限。

### 查询与恢复

```bash
# 查询 npm 官方源上的当前身份；命令不修改凭据。
pnpm whoami --registry https://registry.npmjs.org/

# 查询目标包的维护者，按实际失败的包选择。
pnpm view @zzjtnb/eslint-config maintainers --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config maintainers --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/markdownlint-config maintainers --json --registry https://registry.npmjs.org/
```

身份不对或登录失效时，在真实终端中重新登录，再检查一次身份：

```bash
pnpm login --registry https://registry.npmjs.org/
pnpm whoami --registry https://registry.npmjs.org/
```

如果身份正确但仍不能发布，按 npm 原始错误核对包和组织权限、账号策略及 2FA，不通过清空凭据、取消安全策略或反复 publish 掩盖问题。修正条件后先查询目标精确版本，再恢复尚未完成的请求。

## 查询包版本返回 404，是否说明可以首次发布

不能单凭 404 得出这个结论。先核对拼写、scope、官方 registry、当前身份及包是否曾被取消发布。

```bash
# 查询操作与发布 PUT 是不同阶段，必须分别解释错误。
pnpm view @zzjtnb/eslint-config version --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config version --registry https://registry.npmjs.org/
pnpm view @zzjtnb/markdownlint-config version --registry https://registry.npmjs.org/
```

确认是首次发布时，检查：包名和 scope 可用、账号有权限、版本是有意选择的有效版本、包元信息和发布文件完整、公开 scoped 包的发布命令使用 `--access public`。

## 已经发布过的版本能否覆盖

不能。精确版本号与分发标签是两回事：即使某版本不再是 `latest`，仍不能再次上传同一个包名和版本号。

```bash
# 完整版本列表可发现只看 latest 时遗漏的占用版本。
pnpm view @zzjtnb/stylelint-config versions dist-tags --json --registry https://registry.npmjs.org/

# 2.0.0 替换成需要核对的精确版本。
pnpm view @zzjtnb/stylelint-config@2.0.0 version --registry https://registry.npmjs.org/
```

- 已存在的版本正是本次预期结果：先验证内容和标签，不为“重试”直接升版或重发。
- 已存在但不是要发布的内容：选择未使用的新版本，重新构建、检查和预览。
- 内容正确而标签不对：按后面的标签问题处理，不重新上传同一版本。

确定需要新版本后，按[原始发布流程][commands]的单包升级、同步与验证步骤操作，或按[当前发布流程][current]选择所需范围；不在本页重复维护版本写入流程。

## 取消发布后的版本与 24 小时限制

已经发布再取消发布的版本不能当作未使用版本号。整包取消发布还可能触发 npm 对同名包重新发布的等待限制；按 [npm Unpublish Policy][unpublish-policy]核对当前条件。

所谓 24 小时限制针对整包取消发布后的重新发布，不是“每次正常发布都要等 24 小时才能查询”，也不是等过保护期就能复用已占用版本号。

如果 npm 明确返回保护期错误，停止重试，保留原始响应并按官方政策等待；不要连续升版或循环 publish。远程元信息或 404 不能代替 npm 最终的发布判定，也不能凭固定等待时长认定已恢复。

## 发布命令失败，但 registry 可能已经接收

网络中断、连接退出等失败不保证写入没有发生。应先查询精确版本和标签，再决定是否重试。

先查询精确版本及分发标签，不能仅看上一次命令的退出状态：

```bash
pnpm view @zzjtnb/stylelint-config@2.0.0 version dist.integrity --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config dist-tags --json --registry https://registry.npmjs.org/
```

精确版本查到后还需确认它就是本次预期内容。查询失败或超时只代表尚未确认，不代表可以把发布视为失败后直接重复写入。

## 多包发布只成功了其中一部分

已经发布的包不回滚，未发布的包也不会自动补齐。先逐包查询真实版本，区分命令返回、registry 接收和标签状态。

各包是独立请求，不保证多包原子发布。仅在确认目标精确版本尚未发布后，恢复那个失败包的请求。例如只有 Stylelint 未完成：

```bash
# 先检查该版本，2.0.0 替换为本次实际版本。
pnpm view @zzjtnb/stylelint-config@2.0.0 version --registry https://registry.npmjs.org/

# 确认没有被接收、前置检查仍有效且本地版本正确后，再单独重试。
pnpm --dir packages/stylelint-config publish --access public --tag latest --registry https://registry.npmjs.org/ --no-git-checks
```

ESLint 或 Markdownlint 失败时使用对应目录，不能为修复一个包重新发布所有包。

## OTP / 2FA：一次性码或账号策略导致发布失败

按 [npm 发布安全设置][publishing-2fa]，当前创建和发布包要求 2FA，或符合该包策略的 granular access token。默认设置允许启用 bypass 2FA 的细粒度 token；若包启用“Require two-factor authentication and disallow tokens”，则不能使用 token 发布，无论 token 是否启用 bypass。这里说明正式认证条件，不建议为排障降低包的安全要求。

- 按 npm 当前认证提示完成发布授权；验证码错误、过期、账号 2FA 策略和包发布权限是不同条件，不能只凭“已经登录”认定均已满足。
- npm 要求重新认证时，完成相应认证再核对目标精确版本，确认请求未被接收后才恢复发布；不要反复使用已失效的一次性码。
- token 是否可用于发布以及是否受 2FA、scope 和有效期限制，以账号及包当前的安全设置为准，不为了通过发布降低安全要求。
- 不把 OTP、token 或凭据写入源码、文档、聊天或持久日志。

客户端的非交互错误和本项目脚本的终端限制不是 npm 账号策略本身，分别按[当前发布流程][current]或[原生命令使用问题][commands]处理。

## registry 是镜像源，或发布成功后镜像查不到

先检查默认值，再在查询、安装与发布时按实际目标显式指定官方源：

```bash
pnpm config get registry
pnpm view @zzjtnb/stylelint-config version --registry https://registry.npmjs.org/
```

不能假定所有自定义 registry 都接受 npm 官方账号，或都支持对外发布。本项目的发布命令显式指向 npm 官方源；不要为了本次发布擅自改全局 registry 或凭据。

官方源能查到目标精确版本、镜像查不到时，应排查镜像同步，不直接重发。官方源也查不到时，按精确版本、账号、包名和原始错误继续定位。

## 发布成功但 npm 页面搜索不到包

npm 页面、搜索索引和镜像不是同一条验证链。先查官方 registry 的精确版本与标签；仅看到包名或旧 `latest` 不能证明本次版本已发布。

如果 registry 已返回本次目标版本，进一步核对元信息与真实安装，而不是等待固定秒数后假定成功。完整查询和隔离安装步骤见[原始发布流程的发布后核验][verify]。

## 如何验证发布是否真正成功

至少区分以下证据：

1. 本地 publish 命令的退出状态；
2. npm 官方 registry 能查询到本次精确版本；
3. 分发标签指向预期版本；
4. 该版本元信息、依赖和入口正确；
5. 隔离消费项目安装精确版本后，真实 lint 输入按预期工作。

```bash
# 选择实际发布的包与版本，不只查询最新默认值。
pnpm view @zzjtnb/stylelint-config@2.0.0 version peerDependencies dependencies engines exports --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config dist-tags --json --registry https://registry.npmjs.org/
```

安装、文件保存及实际输入检查见[发布后核验][verify]；临时目录放工作区 `.tmp/`，使用新目录，不清空旧记录。

需要调查完整元信息，而不是只看上面选定的字段时，可以查询整个包文档。以下示例查询默认标签；核对本次发布时，在包名后加上本次精确版本：

```bash
pnpm view @zzjtnb/eslint-config --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/markdownlint-config --json --registry https://registry.npmjs.org/
```

## 预发布版本误设为 latest，或消费者没有装到 next

npm 的版本号与 dist-tag 各自独立：beta 是版本的一部分，next 是指向某版本的标签，不是 Git tag。发布测试版本时显式使用 next 等测试标签，不要让测试内容意外成为 latest 的默认稳定安装。

先用 `pnpm view <包名> dist-tags --json --registry https://registry.npmjs.org/` 核对标签实际指向；版本存在而标签错误时，按下一节处理，不重新上传同一版本。创建各包测试版本的完整命令归[原始发布流程][commands]。

消费方选择测试标签：

```bash
pnpm add -D eslint @zzjtnb/eslint-config@next --registry https://registry.npmjs.org/
pnpm add -D stylelint @zzjtnb/stylelint-config@next --registry https://registry.npmjs.org/
pnpm add -D markdownlint-cli2 @zzjtnb/markdownlint-config@next --registry https://registry.npmjs.org/
```

三条按实际需要选择，不要求同时安装。beta 测试完成后发布稳定版本或调整标签，要单独核对版本内容及其外部影响。

## 版本存在，但 latest / next 标签不对

先查全部标签和精确版本。仅在确认已发布内容正确、只是标签指向有误且拥有权限时，才调整标签；这会影响消费者默认安装，是对外写操作。

```bash
pnpm view @zzjtnb/stylelint-config dist-tags --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config@2.0.0 version --registry https://registry.npmjs.org/

# 确认后才把 latest 指向这个已存在的正确稳定版本，不重新 publish。
pnpm dist-tag add @zzjtnb/stylelint-config@2.0.0 latest --registry https://registry.npmjs.org/
```

如果包内容本身错误，改标签并不能修复旧版本；应发布修复版本，并按下节处理问题版本。

## 发布后发现问题：deprecate 还是 unpublish

优先考虑向消费者清晰提示问题、发布修复版，而不是为重用版本号删除旧版本。下面的版本和包名必须替换为实际问题对象；弃用会影响包的公开状态。

```bash
# 只在确认该版本确实有问题后执行，不对整个包或所有版本批量弃用。
pnpm deprecate @zzjtnb/stylelint-config@2.0.0 "该版本存在已确认问题，请升级到已验证的修复版本。" --registry https://registry.npmjs.org/
pnpm deprecate @zzjtnb/eslint-config@2.0.0 "该版本存在已确认问题，请升级到已验证的修复版本。" --registry https://registry.npmjs.org/
pnpm deprecate @zzjtnb/markdownlint-config@1.0.0 "该版本存在已确认问题，请升级到已验证的修复版本。" --registry https://registry.npmjs.org/
```

修复后选择新版本，重新构建和检查，按所选发布方式发布，再核对精确版本及标签。不要不经核对执行“全包再升一次 patch”。

`unpublish` 不是回滚本地代码，也不能释放已占用版本号；整包移除可能破坏现有消费者。按 [npm Unpublish Policy][unpublish-policy]：

- 发布未满 72 小时的新包：npm 公共 registry 中没有其他包依赖它时，可按政策取消发布。
- 超过 72 小时：必须同时满足公共 registry 中没有其他包依赖、过去一周下载量少于 300、只有一位 owner / maintainer。
- 被移除的 `包名@版本` 永久不能复用；整包所有版本都移除后，24 小时内不能以同名包发布任何新版本。
- 不满足移除条件时，可使用 `deprecate` 给消费者保留下载能力并提示迁移；它不是删除，也不会改写已经发布的内容。

实际移除前仍须确认精确目标、依赖影响、权限与当前官方政策。本页不提供无确认的整包删除捷径。
