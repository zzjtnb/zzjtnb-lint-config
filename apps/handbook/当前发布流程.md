# 当前发布流程

本文面向使用本仓库交互发布脚本的维护者，按当前 `scripts/release/` 脚本、根及公开包的 `package.json` 核对。当前交互入口为 `pnpm release`；下列命令仅为操作说明，本文件不会执行安装或发布。

不使用交互脚本、需要自行选择版本和标签时，按[原始发布流程][commands]逐条执行原生命令。npm 官方发布机制与通用错误只在[发布常见问题][faq]维护；本脚本自身的提示、限制和恢复记录在本文。

## 发布范围

| 包 | 目录 | 发布内容 |
| --- | --- | --- |
| `@zzjtnb/eslint-config` | `packages/eslint-config` | ESM 配置和 TypeScript 声明 |
| `@zzjtnb/stylelint-config` | `packages/stylelint-config` | ESM 配置和 TypeScript 声明 |
| `@zzjtnb/markdownlint-config` | `packages/markdownlint-config` | 带注释的 JSONC 规则，无构建步骤 |

脚本默认让本次所选包统一同号，也支持逐包设置不同版本。根目录、docs、Playground、internal 等私有 workspace 不发布。

## 使用前提

1. 在仓库根目录工作，Node.js 与 pnpm 满足根 `package.json` 的 `engines` 和 `packageManager`；这与消费项目安装公开包的环境要求不同。
2. 已安装项目依赖，且所选包的源码、规则和说明已准备完成。
3. 使用真实交互终端，标准输入和标准输出均为 TTY，且未设置 `CI` 环境变量。
4. npm 账号拥有所选包的发布权限；发布过程中能完成账号要求的登录和 OTP / 2FA。
5. 已确认本次版本、检查范围以及发布 npm 的意图。脚本会改本地版本、同步依赖、构建所选 TypeScript 包并对外发布，不是只读预检命令。

```bash
# 查看环境，要求以根 package.json 为准。
node --version
pnpm --version

# 首次使用或依赖发生变化时，先审查清单和锁文件，再安装。
pnpm install

# 只显示用法，不登录、不改版、不发布。
pnpm release --help
```

`pnpm install` 可能更新锁文件、链接依赖并执行安装生命周期。已有有效安装时，不为每次查看帮助重复安装；仅检查且不允许自动同步时，可使用 `pnpm --config.verifyDepsBeforeRun=error run release --help`。

## 最短操作路径

```bash
# 在真实交互终端启动，按下面的小节逐步确认。
pnpm release
```

整个过程依次为：检查登录 → 选择发布范围（默认全部三个包）→ 查询版本 → 选择并确认版本计划（默认统一同号）→ 写入版本并同步依赖 → 检查所选包 → 预览包内容 → 逐包发布 → 手动核验远程结果。

本地版本已经按本次发布准备好时，版本菜单会提供“使用当前版本”，不需要为了运行脚本再改一次版本。

## 第一步：检查 npm 登录

脚本先对 npm 官方源执行 `pnpm whoami`。能输出账号名称即视为已登录，并显示该账号，再进入发布范围选择；不会先发布后要求补登录。

未登录或账号查询失败时，可以选择：

- **登录**：进入 npm 官方登录流程，结束后再次检查；
- **重试**：只重新查询登录状态；
- **中止**：结束本次流程。

登录状态不等于拥有目标包的发布权限。权限、scope、账号策略及发布阶段的 401 / 403 / 404，见[发布常见问题][faq]。

## 第二步：选择本次发布的包

菜单第一项即默认项，直接回车发布全部三个公开包：

| 选项 | 快捷键 | 范围 |
| --- | --- | --- |
| 发布全部包（默认） | `a` | ESLint、Stylelint、Markdownlint 三个包，按此顺序检查和发布 |
| 仅发布 ESLint | `e` | `@zzjtnb/eslint-config` |
| 仅发布 Stylelint | `s` | `@zzjtnb/stylelint-config` |
| 仅发布 Markdownlint | `m` | `@zzjtnb/markdownlint-config` |

菜单支持方向键、Enter 和显示的字母快捷键。只选择一个包时，后续版本、检查、打包预览与发布只针对该包，不因无关文档站或 Playground 构建失败而扩大发布范围。

非交互终端、CI 或管道输入会在登录、版本写入和发布之前退出，状态码为 `1`；不会把管道内容作为菜单答案。`--help` 不受此限制，成功时返回 `0`。

## 第三步：核对本地与远程版本

脚本显示每个所选包的本地版本及 npm 状态。远程查询使用 `https://registry.npmjs.org/`，不会因为本机默认使用其他镜像而把发布写到镜像源。

交互脚本只支持稳定版本 `major.minor.patch`：三部分均为无前导零的非负安全整数，例如 `1.2.3`。预发布、构建元信息或不完整版本不在脚本支持范围内；`beta` / `next` 发布使用[原生命令流程][commands]，不能强行交给此脚本。

查询显示“未找到”只是脚本看到的 registry 状态，不替代 npm 最终的发布判定；404、版本不可复用和保护期等官方原因统一见[发布常见问题][faq]。

## 第四步：选择版本计划

脚本先询问默认版本是否可用。选择多个包时默认统一同号；只选一个包时就是该包的版本。

| 选项 | 快捷键 | 结果 |
| --- | --- | --- |
| 使用当前版本 | `k` | 仅在可直接使用时出现：所选包中最高的本地版本高于各包 npm `latest`，且没有被任何所选包占用。各包已同号时不改写；上次中途停止只写入了部分包时，用它统一其余包，不再次递增 |
| patch / minor / major | `p` / `m` / `j` | 取所选包本地版本与 npm `latest` 中的最高值，按所选级别递增后统一使用。菜单直接显示结果，例如三个包为 `1.0.4`、`1.0.4`、`1.0.0` 时，patch 为 `1.0.5` |
| 自定义版本 | `c` | 输入完整 `x.y.z`，所选包统一使用；直接回车返回菜单 |
| 按各包分别设置 | `i` | 仅多包时出现。逐包选择保持、patch / minor / major（基于该包本地与 npm `latest` 的较高者）或自定义，各包可以不同号 |
| 中止 | `a` | 退出，不修改版本 |

“使用当前版本”可用时它是默认项，否则默认项是统一 patch。

| 级别 | 适用情况 |
| --- | --- |
| patch | 向后兼容的修复、文档或类型修正 |
| minor | 向后兼容的新能力或新增支持 |
| major | 破坏性变更、移除公开能力、提高环境要求等需要迁移的变化 |

对 lint 配置包而言，新增或收紧默认规则也可能破坏消费项目现有检查，不能仅因改动行数少就认定为 patch。

每个目标版本都要满足：不是 `0.0.0`、高于该包 npm `latest`、不在 npm 已发布版本中，也不是曾发布后被取消的版本。任一所选包不满足时，脚本列出原因并返回版本选择，不写入文件。

选定后脚本列出版本计划，例如：

```text
版本计划：
- @zzjtnb/eslint-config: 1.0.4 → 1.0.5（npm 1.0.4）
- @zzjtnb/stylelint-config: 1.0.4 → 1.0.5（npm 1.0.4）
- @zzjtnb/markdownlint-config: 1.0.0 → 1.0.5（npm 1.0.0，跳过中间版本）
```

统一同号会让版本较低的包跳过中间版本，计划中会明确标出，这是有意的选择，不会阻止发布。确认后才写入；也可以返回重新选择或中止。

## 第五步：写入版本并同步依赖

只改写版本与计划不同的包，命令使用 `--no-git-tag-version --no-git-checks`，随后执行一次 `pnpm install` 同步工作区依赖。

- 某个包写入失败时立即停止：已写入的包不回滚，也不重复改写。修复后重新运行，在版本菜单选择“使用当前版本”或输入目标版本，不要整批再次递增。
- 依赖同步失败时只重试 `pnpm install`，不再次改写版本。
- 写入后重新读取本地版本并与计划核对，不一致时停止。

## 第六步：执行所选包的检查

| 包 | 自动检查 |
| --- | --- |
| ESLint | 构建 → 类型检查 → 包内 ESLint → 包内 Markdown |
| Stylelint | 构建 → 类型检查 → 包内 ESLint → 包内 Markdown |
| Markdownlint | 包内 ESLint → 包内 Markdown；不执行不存在的构建或类型生成 |

检查失败时只允许重试当前检查或中止，没有“跳过失败继续发布”。这些检查不自动修复源码；需要修改文件时，先处理问题再重试。

根级全量测试、源码消费测试、docs / Playground 验证不属于脚本自动执行项。发布前应按本次改动另外完成必要验证，不能把包内 lint 通过等同于整仓或所有消费场景通过。

需要包内格式化时，在另一个已确认作用范围的步骤执行：

```bash
pnpm --filter @zzjtnb/eslint-config run format
pnpm --filter @zzjtnb/stylelint-config run format
pnpm --filter @zzjtnb/markdownlint-config run format
```

## 第七步：预览打包内容

脚本对每个所选包执行其 `release:pack`，当前对应 `pnpm pack --dry-run`。应查看输出，而不是只看退出状态：

- ESLint、Stylelint 应包含正确的 ESM 入口、声明、双语 README 与包元信息；
- Markdownlint 应包含 `index.jsonc`、双语 README 与包元信息；
- 不应包含 node_modules、测试夹具、缓存和临时文件；
- 许可证、依赖和入口与清单相符。

ESLint 和 Stylelint 已在第六步构建；仅预览旧 dist，不能证明当前源码可以发布。

## 第八步：逐包正式发布

脚本在对应包目录直接执行 `pnpm publish`，使用 `public` 访问级别、`latest` 分发标签、npm 官方源和 `--no-git-checks`，并保留真实终端供 OTP 交互。

每次尝试前重新查询 registry：

- 目标版本已经是 `latest`：视为已确认接收，跳过重复发布；
- 本地版本低于远程 `latest`：停止，由维护者核对；
- 目标版本已存在但标签不同，或曾被取消发布：停止，不覆盖该版本；
- 状态查询失败：重试查询或中止，不在未知状态下发布。

发布命令失败后，选择重试会先重新查状态，不直接重复写入。已经发布成功的包不回滚。

## 第九步：发布后手动核验

脚本最后打印 npm 页面和查询命令，**不自动完成最终远程版本或真实安装验证**。命令结束、registry 接收、页面索引更新和消费者成功安装是不同结果。

```bash
# 核对实际发布的包；未选择的包不要求产生新版本。
pnpm view @zzjtnb/eslint-config version --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config version --registry https://registry.npmjs.org/
pnpm view @zzjtnb/markdownlint-config version --registry https://registry.npmjs.org/
```

需要核对完整版本、标签、元信息及真实安装时，按[原始发布流程的发布后核验][verify]执行。页面搜索不到、镜像同步慢或查询超时不代表可以重复发布同一版本，见[发布常见问题][faq]。

## 中止后如何恢复

- **检查失败**：修正源码或环境，再重试该检查；不要删断言或跳过失败制造通过。
- **版本写入部分成功**：核对各包 `package.json` 和锁文件，重新运行后选择“使用当前版本”或输入目标版本统一其余包，不整批再升一次。
- **依赖同步失败**：核对依赖和策略，修正后同步，不重复递增版本。
- **只有部分包发布成功**：先核对 registry，再重启脚本只选择尚未完成的包；重新选择已成功包可能被当作新一轮发布而升级版本。
- **发布命令非零但版本已经存在**：核对该精确版本与标签，不能仅凭退出码盲目重发。

更详细的脚本使用问题和恢复方式见下节；npm 官方错误及 registry 查询方法见[发布常见问题][faq]。

## Git 与远程发布的边界

脚本不会自动 commit、tag、push 或创建 GitHub Release，不要求工作区干净。版本和锁文件修改会留在本地；中止不等于撤销已发生的修改，更不能撤销已经上传到 npm 的包。是否另行记录 Git 版本由维护者决定。

## 现行脚本分层

| 层级 | 当前实际入口与职责 |
| --- | --- |
| 根目录 | `release` 调用 `node scripts/release/index.js`；入口串联同目录按职责拆分的模块，完成选择范围、版本处理、检查和发布 |
| ESLint / Stylelint 包 | 有 `build`、`typecheck`、`lint:eslint`、`format`、`version:patch/minor/major`、`release:pack/publish/verify` 等包级脚本 |
| Markdownlint 包 | 只有当前实际声明的 `lint:eslint`、`format`、`release:pack`；无需 build/typecheck，版本和直接发布使用 pnpm 原生命令 |
| Turbo | 可调度工作区任务，但不是本交互脚本的发布转发层；不应为执行旧命令给根清单补造聚合脚本 |

脚本按包目录生成所选检查，检查步骤见第六步；版本写入使用 pnpm 原生命令，不依赖三个包都有 `version:*` 脚本。发布也在包目录直接调用 pnpm，以保留 OTP 终端。

统一同号、自定义统一版本和逐包版本都在第四步菜单中完成，不需要先手动改版本。部分包已经发布成功后恢复时，只选择尚未完成的包，不把已发布的包混入恢复范围。

## 脚本使用问题与恢复

### 如何先确认自己使用的是哪种发布方式

| 情况 | 应核对的入口 |
| --- | --- |
| 根目录执行 `pnpm release`，出现菜单 | 本项目交互脚本；支持稳定版本与 `latest` |
| 逐条执行 `pnpm --dir packages/<包> version / publish` | 原生命令；由维护者负责检查顺序和分发标签 |
| 执行 `pnpm --filter <包> run <脚本>` | package.json 中的包级脚本，不等同于 pnpm 原生子命令 |

根目录没有 `release:check`、`release:whoami`、`release:publish`、`release:verify` 或 `version:patch` 聚合脚本。不要把旧文档中的这些名称当作当前可执行入口；例如账号查询直接使用 `pnpm whoami --registry https://registry.npmjs.org/`。

### 版本写入失败，为什么不能整批再升一次

`version` 和 `install` 都可能已部分完成。例如计划把三个包统一为 `1.0.5`，ESLint 已写入、Stylelint 写入失败；若重新整批选 patch，会得到 `1.0.6`，与已写入的 ESLint 不再对应原计划。

```bash
# 只读取各包当前版本，不改文件。
node --input-type=module -e 'import {readFileSync} from "node:fs"; for (const name of ["eslint-config", "stylelint-config", "markdownlint-config"]) { const p = JSON.parse(readFileSync(`packages/${name}/package.json`, "utf8")); console.log(p.name, p.version) }'
```

核对后重新运行脚本：只要已写入的最高版本仍可发布，版本菜单会把“使用当前版本”作为默认项，用它统一其余包；也可以用自定义版本输入原计划版本。依赖同步失败只重试同步，不再次递增版本，更不能以删除锁文件或关闭安全策略代替定位原因。

### 本地版本高于远程，是否必须降回去

不必须。跳号可能是有意安排，也可能是重复升级或手工错误，应先核对变更和已发布历史。

- 脚本的版本计划会标出“跳过中间版本”；有意跳号时直接确认，不是有意的就选择 patch / minor / major 或自定义版本修正。
- 统一同号时，版本较低的包跳号是预期结果，例如 Markdownlint 从 `1.0.0` 统一到 `1.0.5`。
- 不想同号时，选择“按各包分别设置”。

### 为什么脚本在 CI、管道或非交互终端中退出

当前脚本要求 stdin、stdout 都为 TTY，且没有设置 `CI`，以保留菜单、登录和 OTP 的真实交互。它不是无人值守 CI 发布器，也不会把管道内容当作答案。

```bash
# 帮助可以在非交互环境运行，不执行发布。
pnpm release --help
```

不要通过伪造 TTY 或塞入管道答案绕过限制。需要无人值守发布时应另行确认认证与发布策略；本文的原生命令能力不等于已经配置好了 CI 凭据或自动发布授权。

### 报找不到 `release:check`、`release:whoami` 等脚本

核对根 `package.json` 的实际 scripts，不凭旧记录补造入口。当前根只提供 `release` 聚合入口；包级脚本以该包的清单为准，Markdownlint 没有两个 TypeScript 包的全部脚本。

- 交互发布执行 `pnpm release`。
- 原生账号查询执行 `pnpm whoami --registry https://registry.npmjs.org/`。
- 手动 version、pack、publish、远程核验使用[原始发布流程][commands]中的 pnpm 原生命令。

`pnpm run version:patch` 与 `pnpm version patch` 不同：前者要求清单有对应脚本，后者是包管理器原生命令。

### 为什么没有自动等待保护期或自动验证最终版本

当前实现没有专门解析远程保护期错误并定时等待，也没有旧说明中“自动等待约 60 秒后完成最终校验”的功能。发布前查询和发布后的手动核验是不同步骤；结束时打印查询命令不等于已经执行。若 npm 返回具体错误，先中止盲目重试，再按[发布常见问题][faq]核对官方条件。

### 为什么 OTP 交互异常

脚本在包目录直接执行 pnpm 并继承终端。若运行环境又套上管道、任务转发或输出捕获，可能出现包管理器的 `ERR_PNPM_OTP_NON_INTERACTIVE`；恢复真实交互终端后重跑当前步骤，不把 OTP 固定写进脚本。npm 账号的 2FA 要求和验证码错误解释归[发布常见问题][faq]。

### 检查失败：能否跳过、自动修复或改默认规则

先区分源码缺陷、配置错误、依赖不同步和无关 workspace 的问题。脚本的包内检查失败只能重试当前步骤或中止；不自动修复，也不允许跳过后继续发布。

手动检查需要修复时，对已确认的目标使用工具的 `--fix`；共享规则、输入和断言不能仅为“通过”而删减。全仓失败不自动证明某个包无法发布，但目标包的必要构建、类型和消费证据也不能省略。
