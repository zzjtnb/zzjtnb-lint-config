# 本地调试

本文档说明如何把当前仓库三个公开配置包 link 到业务项目中调试。当前入口以各包 `package.json` 为准：

| 包 | link 读取的实际入口 | 修改后是否构建 | 消费方工具 |
| --- | --- | --- | --- |
| `@zzjtnb/eslint-config` | `dist/index.mjs` 和 `dist/index.d.ts` | TypeScript 源码变更后构建 | `eslint`，版本满足 peer 要求 |
| `@zzjtnb/stylelint-config` | `dist/index.mjs` 和 `dist/index.d.ts` | TypeScript 源码变更后构建 | `stylelint`，版本满足 peer 要求 |
| `@zzjtnb/markdownlint-config` | `index.jsonc` | 不构建，直接读取共享规则 | 例如 `markdownlint-cli2`；本包无 peer dependency |

三个包可独立选择。下面保留单包、组合、tarball 和恢复操作；不因新增 Markdownlint 删除已有 ESLint / Stylelint 的调试路径。

示例业务项目：

```text
/path/to/your-app
```

示例业务文件：

```text
/path/to/your-app/src/path/to/file.ts
```

## 适用场景

本地 link 调试适合这些情况：

- 修改了 `packages/eslint-config/src`，想立刻在业务项目验证 ESLint 行为。
- 修改了 `packages/stylelint-config/src`，想立刻在业务项目验证 Stylelint 行为。
- 修改了 `packages/markdownlint-config/index.jsonc`，想验证 Markdown 规则的继承、覆盖与修复。
- 修改了配置包的 TypeScript 源码，想在业务项目验证编辑器类型提示。
- 不想先发 npm 版本，只想在真实项目里试规则。

## 推荐方式

推荐使用 pnpm 的 `link:` 协议。

原因：

- 不依赖 npm 发布。
- 不依赖 git tag。
- 不需要全局 link 状态。
- `package.json` 里能明确看到当前依赖来自哪个本地路径。
- ESLint / Stylelint 修改 TypeScript 源码后先构建，业务项目读取最新 dist；Markdownlint 通过 symlink 直接读取最新 `index.jsonc`，不能对它执行不存在的 build。

## 准备变量

下面命令都用变量表示路径，避免重复写长路径。

```bash
# 当前 lint 配置仓库路径。
LINT_REPO="/path/to/zzjtnb-lint-config"

# 需要调试的业务项目路径。
APP_REPO="/path/to/your-app"

# 需要重点验证的业务文件。
TARGET_FILE="src/path/to/file.ts"

# 需要验证的 Markdown 文件；应是项目中实际存在、未被忽略的文档。
MARKDOWN_FILE="docs/example.md"
```

## 先准备本仓库

```bash
# 在 lint 配置仓库安装依赖，确保本地包自己的 dependencies 可被解析。
pnpm --dir "$LINT_REPO" install

# 仅 ESLint、Stylelint 读取 dist，修改它们的 TypeScript 源码后构建；只调试其中一个时只执行对应命令。
# Markdownlint 直接导出 index.jsonc，不需要也没有 build 脚本。
pnpm --dir "$LINT_REPO" --filter @zzjtnb/eslint-config run build
pnpm --dir "$LINT_REPO" --filter @zzjtnb/stylelint-config run build

# 验证源码类型、lint 和消费契约，不能以 build 成功代替这些检查。
pnpm --dir "$LINT_REPO" exec tsc --noEmit -p packages/eslint-config/tsconfig.json
pnpm --dir "$LINT_REPO" exec tsc --noEmit -p packages/stylelint-config/tsconfig.json
pnpm --dir "$LINT_REPO" exec eslint packages --max-warnings 0
pnpm --dir "$LINT_REPO" exec vitest run --project integration --project packages

# 检查各自发布清单，不上传 npm。
pnpm --dir "$LINT_REPO/packages/eslint-config" run release:pack
pnpm --dir "$LINT_REPO/packages/stylelint-config" run release:pack
pnpm --dir "$LINT_REPO/packages/markdownlint-config" run release:pack
```

只调试 Markdownlint 时不运行上面的两个 TypeScript 构建和类型检查，改为验证 JSONC、消费行为与发布文件：

```bash
pnpm --dir "$LINT_REPO" exec eslint packages/markdownlint-config --max-warnings 0
pnpm --dir "$LINT_REPO" exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/markdownlint-config/**/*.md"
pnpm --dir "$LINT_REPO" exec vitest run tests/integration/consumer-configs.test.ts --project integration -t Markdownlint
pnpm --dir "$LINT_REPO/packages/markdownlint-config" pack --dry-run
```

## Link ESLint 配置包

如果业务项目要调试 ESLint 配置，执行：

```bash
# 把业务项目里的 @zzjtnb/eslint-config 指向本地 packages/eslint-config。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/eslint-config@link:$LINT_REPO/packages/eslint-config"
```

业务项目需要有 `eslint`，因为 `eslint` 是 peer dependency：

```bash
# 如果业务项目还没安装 eslint，补充安装。
pnpm --dir "$APP_REPO" add -D eslint
```

确认业务项目的 `eslint.config.ts` 使用本包：

```ts
// 导入本地 link 后的 @zzjtnb/eslint-config。
import { zzjtnb } from '@zzjtnb/eslint-config'

// 使用默认配置。
export default zzjtnb()
```

验证目标文件：

```bash
# 在业务项目中对目标文件执行 ESLint，并自动修复可修复问题。
pnpm --dir "$APP_REPO" exec eslint "$TARGET_FILE" --fix
```

查看 ESLint 最终配置的方法见本文末尾[不确定最终规则是否生效](#不确定最终规则是否生效)；保留诊断输出后，可对比本地规则修改前后的结果。

如果你修改了本仓库的：

```text
packages/eslint-config/src/**/*.ts
packages/eslint-config/package.json
```

只改源码时直接构建再验证；若依赖清单也变更，先完成下面两处依赖同步，再构建，避免新依赖尚未安装就运行检查。

```bash
# 仅依赖变更时：审查后先同步本仓库依赖，再刷新消费项目的依赖状态。
pnpm --dir "$LINT_REPO" install
pnpm --dir "$APP_REPO" install

# 依赖已就绪或只改源码时：构建后重新运行真实业务输入。
pnpm --dir "$LINT_REPO" --filter @zzjtnb/eslint-config build
pnpm --dir "$APP_REPO" exec eslint "$TARGET_FILE" --fix
```

## Link Stylelint 配置包

如果业务项目要调试 Stylelint 配置，执行：

```bash
# 把业务项目里的 @zzjtnb/stylelint-config 指向本地 packages/stylelint-config。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/stylelint-config@link:$LINT_REPO/packages/stylelint-config"
```

业务项目需要有 `stylelint`，因为 `stylelint` 是 peer dependency：

```bash
# 如果业务项目还没安装 stylelint，补充安装。
pnpm --dir "$APP_REPO" add -D stylelint
```

确认业务项目的 `stylelint.config.ts` 使用本包：

```ts
// 导出 Stylelint 配置对象。
export default {
  // 使用本地 link 后的 @zzjtnb/stylelint-config。
  extends: [
    '@zzjtnb/stylelint-config',
  ],
}
```

如果业务项目脚本使用 `**/*.{css,scss,vue,html}` 这类全仓库宽 glob，命令中保留 `--config stylelint.config.ts`，让 Stylelint 始终使用项目根配置和本包内置忽略规则。

验证样式文件：

```bash
# 在业务项目中执行 Stylelint；cacheLocation 保持项目标准缓存路径。
pnpm --dir "$APP_REPO" exec stylelint "**/*.{css,scss,vue,html}" --config stylelint.config.ts --cache-location node_modules/.cache/.stylelintcache
```

如果你修改了本仓库的：

```text
packages/stylelint-config/src/**/*.ts
packages/stylelint-config/package.json
```

只改源码时直接构建再验证；若依赖清单也变更，先完成下面两处依赖同步，再构建。

```bash
# 仅依赖变更时：审查后先同步本仓库依赖，再刷新消费项目的依赖状态。
pnpm --dir "$LINT_REPO" install
pnpm --dir "$APP_REPO" install

# 依赖已就绪或只改源码时：构建后重新运行真实业务输入。
pnpm --dir "$LINT_REPO" --filter @zzjtnb/stylelint-config build
pnpm --dir "$APP_REPO" exec stylelint "**/*.{css,scss,vue,html}" --config stylelint.config.ts --cache-location node_modules/.cache/.stylelintcache
```

## Link Markdownlint 配置包

```bash
# 共享包仅包含规则数据；CLI2 是消费项目运行检查的工具。
pnpm --dir "$APP_REPO" add -D markdownlint-cli2 "@zzjtnb/markdownlint-config@link:$LINT_REPO/packages/markdownlint-config"
```

在业务项目的 `.markdownlint-cli2.jsonc` 中继承共享包，保留原有扫描范围、忽略和自定义规则；不要覆盖已有项目配置：

```jsonc
{
  "gitignore": true,
  "ignores": ["**/node_modules/**", "**/dist/**"],
  "config": {
    "extends": "@zzjtnb/markdownlint-config",
    // 示例本地覆盖；不需要时移除这项，继续使用共享默认值。
    "MD013": { "line_length": 120 }
  }
}
```

```bash
# 检查实际 Markdown 文件；--fix 仅在确认需要写回时追加。
pnpm --dir "$APP_REPO" exec markdownlint-cli2 "$MARKDOWN_FILE"
```

修改 `packages/markdownlint-config/index.jsonc` 后，重新执行 CLI2 即读取新规则，不构建 dist。长驻编辑器如仍持有旧配置，应重新加载相关扩展或工作区；不能把页面刷新或其他工具重启当作编辑器已重载的证据。修改包元信息或 link 路径后，核对并同步消费项目依赖。

## 同时 Link 多个配置包

只需要原来的 ESLint 与 Stylelint 组合时保留下面两条；新增 Markdownlint 时再加第三条：

```bash
# Link ESLint 配置包。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/eslint-config@link:$LINT_REPO/packages/eslint-config"

# Link Stylelint 配置包。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/stylelint-config@link:$LINT_REPO/packages/stylelint-config"

# 确保 ESLint / Stylelint 对应的 peer 工具存在。
pnpm --dir "$APP_REPO" add -D eslint stylelint

# 同时调试文档规则时再加入 Markdownlint 配置和 CLI2。
pnpm --dir "$APP_REPO" add -D markdownlint-cli2 "@zzjtnb/markdownlint-config@link:$LINT_REPO/packages/markdownlint-config"
```

然后按实际 link 的包分别验证：

```bash
# 验证目标 TypeScript 文件的 ESLint 行为。
pnpm --dir "$APP_REPO" exec eslint "$TARGET_FILE" --fix

# 验证业务项目样式文件的 Stylelint 行为。
pnpm --dir "$APP_REPO" exec stylelint "**/*.{css,scss,vue,html}" --config stylelint.config.ts --cache-location node_modules/.cache/.stylelintcache

# 同时 link Markdownlint 时，验证实际文档及本地规则覆盖。
pnpm --dir "$APP_REPO" exec markdownlint-cli2 "$MARKDOWN_FILE"
```

## 更接近 npm 发布的调试方式

`link:` 适合快速迭代，但它和真实 npm 安装仍有差异。

如果要模拟用户从 npm 安装的效果，推荐用 `pnpm pack` 生成本地 tarball 再安装。

```bash
# 每轮在工作区临时目录中创建新的打包目录，不覆盖或删除旧 tarball。
mkdir -p "$LINT_REPO/.tmp/local-consumer"
PACK_DIR="$(mktemp -d "$LINT_REPO/.tmp/local-consumer/pack.XXXXXX")"

# 打包 ESLint 配置包到临时目录。
pnpm --dir "$LINT_REPO/packages/eslint-config" pack --pack-destination "$PACK_DIR"

# 打包 Stylelint 配置包到临时目录。
pnpm --dir "$LINT_REPO/packages/stylelint-config" pack --pack-destination "$PACK_DIR"

# Markdownlint 直接打包 index.jsonc，不在这里追加 build。
pnpm --dir "$LINT_REPO/packages/markdownlint-config" pack --pack-destination "$PACK_DIR"

# 查看生成的 tgz 文件名。
ls "$PACK_DIR"
```

把 tarball 安装到业务项目：

```bash
# 安装本地打包出来的 ESLint 配置包。
pnpm --dir "$APP_REPO" add -D "$PACK_DIR"/zzjtnb-eslint-config-*.tgz

# 安装本地打包出来的 Stylelint 配置包。
pnpm --dir "$APP_REPO" add -D "$PACK_DIR"/zzjtnb-stylelint-config-*.tgz

# 安装本地打包出来的 Markdownlint 配置包；缺少 CLI2 时一并安装。
pnpm --dir "$APP_REPO" add -D markdownlint-cli2 "$PACK_DIR"/zzjtnb-markdownlint-config-*.tgz
```

然后验证：

```bash
# 验证 ESLint。
pnpm --dir "$APP_REPO" exec eslint "$TARGET_FILE" --fix

# 验证 Stylelint。
pnpm --dir "$APP_REPO" exec stylelint "**/*.{css,scss,vue,html}" --config stylelint.config.ts --cache-location node_modules/.cache/.stylelintcache

# 验证 Markdownlint；使用前面保存的 CLI2 配置和实际文档输入。
pnpm --dir "$APP_REPO" exec markdownlint-cli2 "$MARKDOWN_FILE"
```

选择建议：

| 方式 | 优点 | 缺点 | 适合场景 |
| --- | --- | --- | --- |
| `link:` | ESLint / Stylelint 构建后读取最新 dist；Markdownlint 直接读取最新 index.jsonc。 | 和真实 npm 安装略有差异；只有两个 TypeScript 包需要构建。 | 快速迭代规则。 |
| `pack` tarball | 最接近 npm 发布后的安装效果。 | 每次改动后都要重新 pack 和安装。 | 发布前最终验证。 |

## 恢复业务项目依赖

调试结束后，可以把业务项目从本地 link 恢复到 npm 版本。

```bash
# 恢复 ESLint 配置包为 npm latest 版本。
pnpm --dir "$APP_REPO" add -D @zzjtnb/eslint-config@latest --registry https://registry.npmjs.org/

# 恢复 Stylelint 配置包为 npm latest 版本。
pnpm --dir "$APP_REPO" add -D @zzjtnb/stylelint-config@latest --registry https://registry.npmjs.org/

# 恢复 Markdownlint 配置包为 npm latest 版本。
pnpm --dir "$APP_REPO" add -D @zzjtnb/markdownlint-config@latest --registry https://registry.npmjs.org/
```

如果业务项目需要固定版本，不要用 `latest`，改成明确版本：

```bash
# 恢复 ESLint 配置包到指定版本。
pnpm --dir "$APP_REPO" add -D @zzjtnb/eslint-config@0.1.0 --registry https://registry.npmjs.org/

# 恢复 Stylelint 配置包到指定版本，版本应先核对确实存在。
pnpm --dir "$APP_REPO" add -D @zzjtnb/stylelint-config@0.1.0 --registry https://registry.npmjs.org/

# Markdownlint 独立版本，不要求与另外两个包同号；示例版本也应先核对。
pnpm --dir "$APP_REPO" add -D @zzjtnb/markdownlint-config@1.0.0 --registry https://registry.npmjs.org/
```

## 常见问题

### 业务项目找不到本地配置包

先确认 link 路径真实存在：

```bash
# 检查 ESLint 本地包目录。
ls "$LINT_REPO/packages/eslint-config"

# 检查 Stylelint 本地包目录。
ls "$LINT_REPO/packages/stylelint-config"

# 检查 Markdownlint 的实际 JSONC 入口。
ls "$LINT_REPO/packages/markdownlint-config/index.jsonc"
```

再重新安装：

```bash
# 重新安装业务项目依赖。
pnpm --dir "$APP_REPO" install
```

### 修改本仓库后业务项目没有变化

先确认业务项目依赖确实是 `link:`：

```bash
# 查看业务项目 package.json 里是否写着 link:。
pnpm --dir "$APP_REPO" list @zzjtnb/eslint-config @zzjtnb/stylelint-config @zzjtnb/markdownlint-config --depth 0
```

如果不是 `link:`，重新执行 link 命令：

```bash
# 重新 link ESLint 配置包。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/eslint-config@link:$LINT_REPO/packages/eslint-config"

# 重新 link Stylelint 配置包。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/stylelint-config@link:$LINT_REPO/packages/stylelint-config"

# 重新 link Markdownlint 配置包；规则变更不需要构建。
pnpm --dir "$APP_REPO" add -D "@zzjtnb/markdownlint-config@link:$LINT_REPO/packages/markdownlint-config"
```

### pnpm 运行前依赖校验失败

如果业务项目执行 `pnpm install`，或通过 `pnpm exec` 运行 ESLint、Stylelint、Markdownlint CLI2 时出现
lockfile 供应链策略校验错误，例如 `ERR_PNPM_TRUST_DOWNGRADE`，需要在业务项目根目录处理。

先保留原始错误、版本和依赖信息，确认失败属于消费项目的安装策略还是共享包的实际依赖，不因出现策略错误就删除锁文件或关闭 `trustPolicy`。`pnpm-workspace.yaml` 也用于普通项目的 pnpm 设置，并非只能声明 workspace。

仅验证现有安装时使用：

```bash
# 依赖状态不同步时明确失败，不在检查前隐式安装。
pnpm --config.verifyDepsBeforeRun=error --dir "$APP_REPO" exec eslint "$TARGET_FILE" --fix

# 核对消费项目的 peer dependency。
pnpm --config.verifyDepsBeforeRun=error --dir "$APP_REPO" peers check
```

确需同步依赖时，按以下顺序处理，而不是先清锁文件：

1. 保留完整错误中的包名、版本、registry 和策略字段；用 `pnpm --dir "$APP_REPO" why <报错包名>` 核对来源，确认是否由本配置包引入。
2. 对照消费项目清单、锁文件及允许的安全策略。若远程包的完整性或信任信息变化，先核验来源；不为通过安装直接删除锁文件或关闭 `trustPolicy`。
3. 确认只是已审查的依赖变更尚未同步后，在消费项目执行安装；这可能修改锁文件并运行被允许的安装生命周期。

```bash
# 仅在已核对差异、确认需要同步时执行，不作为所有策略错误的统一修复。
pnpm --dir "$APP_REPO" install
```

1. 如果安装提示依赖构建脚本未获准，核对具体依赖及其真实用途后再审批。不要批量放开未知脚本。

```bash
# 交互选择已确认需要构建的依赖；该命令可能修改项目的构建审批配置。
pnpm --dir "$APP_REPO" approve-builds
```

1. 再次检查 peer dependency，并重新运行目标 lint，确认恢复的是原始使用场景，而不只是安装命令退出成功。

```bash
pnpm --config.verifyDepsBeforeRun=error --dir "$APP_REPO" peers check
pnpm --config.verifyDepsBeforeRun=error --dir "$APP_REPO" exec eslint "$TARGET_FILE" --fix
```

上述 `--dir` 命令等价于先进入消费项目根目录再执行相应命令，不会将操作误作用于配置仓库。恢复后审查 `package.json`、锁文件和构建审批差异；不要在不了解依赖变化时随意提交。

### peer dependency 报错

ESLint 和 Stylelint 把主工具作为 peer dependency；Markdownlint 配置包不声明 peer dependency，但实际检查文档仍需要 CLI2 等执行工具：

| 配置包 | 需要业务项目安装 |
| --- | --- |
| `@zzjtnb/eslint-config` | `eslint` |
| `@zzjtnb/stylelint-config` | `stylelint` |
| `@zzjtnb/markdownlint-config` | 例如 `markdownlint-cli2`，不是该包声明的 peer dependency |

按实际使用的配置包补充安装，不必为了调试一个包安装全部工具：

```bash
# 使用 ESLint / Stylelint 时安装相应 peer 工具。
pnpm --dir "$APP_REPO" add -D eslint stylelint

# 使用 Markdownlint 时安装执行工具；这不是配置包声明的 peer。
pnpm --dir "$APP_REPO" add -D markdownlint-cli2
```

### 不确定最终规则是否生效

ESLint 可以打印目标文件最终配置：

```bash
# 每轮保存到新文件，不覆盖以前的诊断记录。
mkdir -p "$APP_REPO/.tmp/local-consumer"
CONFIG_OUTPUT="$(mktemp "$APP_REPO/.tmp/local-consumer/eslint-config.XXXXXX")"
pnpm --dir "$APP_REPO" exec eslint --print-config "$TARGET_FILE" > "$CONFIG_OUTPUT"
printf '%s\n' "$CONFIG_OUTPUT"
```

Stylelint 可以直接运行目标样式范围，看是否还报预期规则：

```bash
# 执行业务项目样式检查。
pnpm --dir "$APP_REPO" exec stylelint "**/*.{css,scss,vue,html}" --config stylelint.config.ts --cache-location node_modules/.cache/.stylelintcache
```

Markdownlint 应用实际 Markdown 输入验证：选择包含目标规则违规内容的文件，运行下面的检查，核对规则编号、行号和本地覆盖是否符合预期；修正输入后再次运行。不能只凭 JSONC 能解析、包能找到或空目录检查成功判断规则已生效。

```bash
pnpm --dir "$APP_REPO" exec markdownlint-cli2 "$MARKDOWN_FILE"
```

前面的 `MD013` 覆盖示例可用超过 120 字符、且不属于该规则豁免场景的普通段落验证。共享包规则解释以 `packages/markdownlint-config/index.jsonc` 为准，消费方自定义规则和扫描范围仍由本地 CLI2 配置维护。
