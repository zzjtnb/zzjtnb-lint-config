# 原始发布流程

本文提供不依赖本项目交互发布脚本的**原生命令发布方式**，适用于维护者手动确定包、版本、检查步骤与 npm 分发标签。它不是废弃历史，也不要求改用 `pnpm release`。

想由脚本组织检查和交互时，见[当前发布流程][current]。本文记录原生命令自身的使用与恢复；npm 官方发布机制及通用错误集中见[发布常见问题][faq]。本文中的发布、版本变更、安装、Git 和弃用操作均为供维护者主动执行的说明，不会由文档自动执行。

## 包与环境

| 包 | 目录 | 产物 |
| --- | --- | --- |
| `@zzjtnb/eslint-config` | `packages/eslint-config` | `dist/index.mjs`、`dist/index.d.ts` |
| `@zzjtnb/stylelint-config` | `packages/stylelint-config` | `dist/index.mjs`、`dist/index.d.ts` |
| `@zzjtnb/markdownlint-config` | `packages/markdownlint-config` | `index.jsonc`，无需构建 |

只发布这三个公开包；根目录是私有 workspace，docs、Playground、internal 和示例应用不属于 npm 发布范围。以下命令默认从仓库根目录执行，Shell 变量和循环示例使用 Bash / Zsh。

- 仓库开发环境以根 `package.json` 的 `engines` 和 `packageManager` 为准，不复制为消费方的最低环境要求。
- npm 账号需要所选包或其 scope 的发布权限；已登录不等于权限一定足够。
- 发布统一显式指定 npm 官方 registry。
- 原生 `pnpm version`、`pnpm publish` 的参数与本项目同名 package script 不是一回事；本文不用已不存在的根级 `release:*` 或 `version:*` 聚合脚本。

```bash
# 查看 Node.js 与 pnpm 版本，要求以根 package.json 为准。
node --version
pnpm --version

# 查看当前默认 registry；只读，不改配置。
pnpm config get registry
```

本文所有查询、登录和发布命令都显式带 `--registry https://registry.npmjs.org/`，默认 registry 是镜像也不影响发布。只有希望本机日常安装也默认走 npm 官方源时，才修改全局设置；它会影响这台机器上所有项目，不是发布的必要步骤：

```bash
# 可选：把全局默认 registry 设为 npm 官方源，影响本机所有项目。
pnpm config set registry https://registry.npmjs.org/ --location global

# 设置后再次查看，确认生效。
pnpm config get registry
```

```bash
# 查询 npm 官方源上的当前账号；只读，不修改登录状态。
pnpm whoami --registry https://registry.npmjs.org/
```

`whoami` 输出一个 npm 用户名并以状态 `0` 结束，就表示已登录，不需要再执行 login；输出的账号应是拥有目标包发布权限的账号。若报 401、提示需要认证或没有输出用户名，表示未登录或登录已失效，再执行下面的登录：

```bash
# 仅在未登录、登录失效或账号不对时执行：登录 npm 官方源，按终端或浏览器提示完成认证。
pnpm login --registry https://registry.npmjs.org/
```

登录完成后再执行一次 `whoami`，能输出预期用户名才算登录成功。已登录只说明身份可识别，不代表一定拥有目标包的发布权限。命令帮助可通过 `pnpm help version`、`pnpm help pack`、`pnpm help publish` 查看；以下参数以 pnpm 12.15.0 的帮助为准。

## 最短完整流程

下面以仅发布 ESLint 包为例，顺序包含版本、锁文件、构建、验证、预览、发布和远程核验。**确认每一步成功后再执行下一步，不要在失败后整段重跑。** 若既有本地版本已经为本次发布准备好，跳过递增步骤。

```bash
# 1. 首次使用或依赖有变化时，审查后安装；可能执行已有安装生命周期。
pnpm install

# 2. 仅升级当前目标包；不创建 Git commit/tag，也不要求工作区干净。
pnpm --dir packages/eslint-config version patch --no-git-tag-version --no-git-checks

# 3. 同步版本变化后的工作区依赖和锁文件。
pnpm install

# 4. 先生成当前源码对应的 JavaScript 和类型产物。
pnpm --dir packages/eslint-config exec tsdown

# 5. 检查该包源码、类型与 README，不隐式修复。
pnpm exec tsc --noEmit -p packages/eslint-config/tsconfig.json
pnpm exec eslint packages/eslint-config --max-warnings 0
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/eslint-config/**/*.md"

# 6. 查看将发布的文件；dry-run 不上传 npm。
pnpm --dir packages/eslint-config pack --dry-run

# 7. 再核对账号、目标版本是否已存在及当前分发标签。
pnpm whoami --registry https://registry.npmjs.org/
pnpm view @zzjtnb/eslint-config versions dist-tags --json --registry https://registry.npmjs.org/

# 8. 在真实终端中发布，按 npm 提示完成 OTP / 2FA。
pnpm --dir packages/eslint-config publish --access public --tag latest --registry https://registry.npmjs.org/ --no-git-checks

# 9. 查询默认版本，并继续按“发布后核验”查询本次精确版本和标签。
pnpm view @zzjtnb/eslint-config version --registry https://registry.npmjs.org/
```

版本查询失败时先按[发布常见问题][faq]核对，确认远程状态后再继续，不忽略错误。测试与消费验证按改动范围补齐，见后续章节。

## 版本策略：独立版本或手动同号

三个包可以独立发版，不要求版本一致。版本语义遵循 [SemVer][semver]；对于共享 lint 配置，新增默认错误或收紧规则可能让现有消费项目失败，应单独评估破坏性。

| 类型 | 示例 | 适用情况 |
| --- | --- | --- |
| patch | `1.2.3` → `1.2.4` | 向后兼容的修复、文档或声明修正 |
| minor | `1.2.3` → `1.3.0` | 向后兼容的新能力 |
| major | `1.2.3` → `2.0.0` | 破坏性变更、移除能力、需要迁移 |
| prepatch | `1.2.3` → `1.2.4-beta.0` | 下一补丁版的测试版本，需配合 `--preid beta` |
| preminor | `1.2.3` → `1.3.0-beta.0` | 下一次版本的测试版本 |
| premajor | `1.2.3` → `2.0.0-beta.0` | 下一主版本的测试版本 |
| prerelease | `1.3.0-beta.0` → `1.3.0-beta.1` | 继续递增已有预发布版本 |

### 单包升级

```bash
# 仅选择本次实际改动的包；下面三条不是必须一起执行。
pnpm --dir packages/eslint-config version patch --no-git-tag-version --no-git-checks
pnpm --dir packages/stylelint-config version patch --no-git-tag-version --no-git-checks
pnpm --dir packages/markdownlint-config version patch --no-git-tag-version --no-git-checks

# 本轮版本变更后从根目录同步一次依赖。
pnpm install
```

需要 minor 或 major 时，将对应命令中的 `patch` 改成所需级别；不要依次执行三个级别。某包升级成功后另一个包失败，保留成功结果，仅恢复未完成步骤，不整批重新递增。

### 将所选包设置为同一个固定版本

固定版本由维护者核对是否可用；示例 `2.0.0` 不是要求所有包升级到该版本。

```bash
VERSION=2.0.0

# 确实需要三包同号时才一起设置；只需两包时省略第三条。
pnpm --dir packages/eslint-config version "$VERSION" --no-git-tag-version --no-git-checks
pnpm --dir packages/stylelint-config version "$VERSION" --no-git-tag-version --no-git-checks
pnpm --dir packages/markdownlint-config version "$VERSION" --no-git-tag-version --no-git-checks
pnpm install
```

`patch` / `minor` / `major` 基于各包自己的当前版本递增，原版本不同就不保证结果同号。已是目标版本时不要为重试盲目递增；先查询本地与 registry 状态。

### 有限范围的递归升级

需要对相同范围应用相同级别时，可使用 pnpm 原生递归能力。始终显式限制包名，避免影响所有私有 workspace；没有版本参数的 `pnpm version -r` 可能进入 pnpm 的 change-intent 发布管理流程，不等同于下面的显式 patch。

```bash
# 仅递增 ESLint 与 Stylelint，两个包各自按当前版本升 patch。
pnpm --filter @zzjtnb/eslint-config --filter @zzjtnb/stylelint-config -r version patch --no-git-tag-version --no-git-checks
pnpm install
```

需要 minor 或 major 时选择下面对应的一条，不要先 patch 再连续执行其他级别：

```bash
# 向后兼容的新能力：仅升级这两个明确选中的包。
pnpm --filter @zzjtnb/eslint-config --filter @zzjtnb/stylelint-config -r version minor --no-git-tag-version --no-git-checks
pnpm install

# 破坏性变更：与上面的 minor 二选一，不是顺序执行。
pnpm --filter @zzjtnb/eslint-config --filter @zzjtnb/stylelint-config -r version major --no-git-tag-version --no-git-checks
pnpm install
```

要包含 Markdownlint，显式再加它的 `--filter`。递归行为以当前 pnpm 版本为准；希望逐包确认中间结果时，优先使用前面的单包命令。

### 手动编辑 package.json

也可直接编辑目标包的 `version`。编辑后执行 `pnpm install`，再重新构建和验证实际会发布的内容；不要只修改版本字符串就上传旧 dist。

## 发布前验证

### 构建两个 TypeScript 包

只执行本次所选包对应的命令；Markdownlint 没有此步骤。

```bash
pnpm --dir packages/eslint-config exec tsdown
pnpm --dir packages/stylelint-config exec tsdown
```

这两条命令读取各自的 `tsdown.config.ts`，生成现有 exports 契约要求的 `.mjs` 与 `.d.ts`。不要用手动修改 dist、改源码别名或旧构建通过替代本次构建验证。

### 类型、代码与文档检查

```bash
# 源码类型检查。
pnpm exec tsc --noEmit -p packages/eslint-config/tsconfig.json
pnpm exec tsc --noEmit -p packages/stylelint-config/tsconfig.json

# 公开包代码和 JSONC 配置检查；只检查，不写回。
pnpm exec eslint packages --max-warnings 0

# README 及维护说明检查。
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/**/*.md"
```

检查失败先修复再重跑，不跳过失败。需要显式自动修复时，为目标命令追加 `--fix`；`pnpm lint` 本身只检查，不会自动修复。

### 源码消费和包入口测试

```bash
# 从当前源码检查真实 lint 行为和文档示例。
pnpm exec vitest run --project integration

# 按包名检查公开入口；两个 TypeScript 包应已有对应的最新构建产物。
pnpm exec vitest run --project packages
```

入口测试同时验证公开包，因此单包发布时也可能需要另一 TypeScript 包的既有有效产物。若它因无关产物缺失失败，应明确记录缺口，不扩大到发布无关包，也不能伪称已通过。

需要整仓回归时额外执行 `pnpm exec vitest run`。Playground、docs 与内部工具的验证依据本次影响选择，不能将全仓测试等同于目标发布包已经构建或真实安装成功。

### 人工核对清单

- [ ] 包名、版本、description、keywords、repository、bugs 和 license 与本次发布一致。
- [ ] 双语 README 反映实际能力；项目许可证和包声明相符。
- [ ] ESLint、Stylelint 的 `exports` 提供实际存在的 import 与 types 入口，不要求不存在的 default 子项。
- [ ] Markdownlint 导出 JSONC，不要求 dist 或类型声明。
- [ ] `files` 限定发布内容；配置、插件、parser 等真正运行依赖在 dependencies，主工具按契约声明为 peer dependency。
- [ ] devDependencies 可用于构建和测试，不应为了“没有开发依赖”而把它们错误搬入运行时依赖。
- [ ] 当前源码的必要检查和测试通过，没有用旧产物代替新源码验证。

## 打包内容预检

```bash
# 只预览本次准备发布的包；不会上传 npm。
pnpm --dir packages/eslint-config pack --dry-run
pnpm --dir packages/stylelint-config pack --dry-run
pnpm --dir packages/markdownlint-config pack --dry-run
```

两个 TypeScript 包应包含双语 README、包元信息、`dist/index.mjs` 和 `dist/index.d.ts`；Markdownlint 应包含双语 README、包元信息和 `index.jsonc`。实际清单和许可证收录以 dry-run 为准，不凭文件名或 package.json 单独认定。

node_modules、测试、fixtures、缓存及临时文件不应成为发布内容。dry-run 只预览，不能证明包已发布，也不能代替干净消费项目的加载检查。

## 正式发布

### 发布两个包或全部包

```bash
# 每条命令单独确认结果，再执行下一条；不要以循环盲目重试写入。
pnpm --dir packages/eslint-config publish --access public --tag latest --registry https://registry.npmjs.org/ --no-git-checks
pnpm --dir packages/stylelint-config publish --access public --tag latest --registry https://registry.npmjs.org/ --no-git-checks

# 本次也需要发 Markdownlint 时才执行。
pnpm --dir packages/markdownlint-config publish --access public --tag latest --registry https://registry.npmjs.org/ --no-git-checks
```

### 只发布一个包

只执行对应包目录的那条命令；不必运行另外两个包的 publish，也不要在根目录使用无过滤的递归发布。

| 参数 | 含义 |
| --- | --- |
| `--dir packages/<包目录>` | 在目标包目录执行，而不是发布根私有 workspace |
| `publish` | 上传当前包，属于对外写操作 |
| `--access public` | 显式公开发布 scoped 包 |
| `--tag latest` | 将该版本作为默认安装标签；不是 Git tag |
| `--registry https://registry.npmjs.org/` | 明确写入 npm 官方源 |
| `--no-git-checks` | 不以 Git 工作区干净为发布条件，不代表跳过构建和消费检查 |

在真实终端中完成 npm 要求的 OTP / 2FA，不将一次性码或 token 写进文档、源码或日志。失败后先查询精确版本和标签；非零退出可能发生在 registry 已接收之后。

## 预发布版本与 next 标签

原生命令可发布 beta / next。只对实际需要的包执行；普通稳定发布不执行这一节。

### Stylelint 测试版本

```bash
# 从当前稳定版进入下一个 patch 的 beta；已有 beta 继续发版时使用 prerelease。
pnpm --dir packages/stylelint-config version prepatch --preid beta --no-git-tag-version --no-git-checks
pnpm install

# 必须重新构建、检查和预览测试版本。
pnpm --dir packages/stylelint-config exec tsdown
pnpm exec tsc --noEmit -p packages/stylelint-config/tsconfig.json
pnpm exec eslint packages/stylelint-config --max-warnings 0
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/stylelint-config/**/*.md"
pnpm --dir packages/stylelint-config pack --dry-run

# next 与 latest 分离，避免测试版本成为默认稳定安装。
pnpm --dir packages/stylelint-config publish --access public --tag next --registry https://registry.npmjs.org/ --no-git-checks

# 核对标签；用户选择安装 next 时，仍需安装相应 peer 工具。
pnpm view @zzjtnb/stylelint-config dist-tags --json --registry https://registry.npmjs.org/
```

### ESLint 测试版本

同样可以单独发布 ESLint 测试版本，先完成该包的检查，再使用 next 标签：

```bash
# 选择下个 patch 的 beta；已有 beta 继续递增时用 prerelease。
pnpm --dir packages/eslint-config version prepatch --preid beta --no-git-tag-version --no-git-checks
pnpm install
pnpm --dir packages/eslint-config exec tsdown
pnpm exec tsc --noEmit -p packages/eslint-config/tsconfig.json
pnpm exec eslint packages/eslint-config --max-warnings 0
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/eslint-config/**/*.md"
pnpm --dir packages/eslint-config pack --dry-run

# 发布测试标签，不更改 latest 的稳定安装入口。
pnpm --dir packages/eslint-config publish --access public --tag next --registry https://registry.npmjs.org/ --no-git-checks
pnpm view @zzjtnb/eslint-config dist-tags --json --registry https://registry.npmjs.org/
```

### Markdownlint 测试版本

Markdownlint 直接发布 JSONC，不执行不存在的构建和类型生成：

```bash
pnpm --dir packages/markdownlint-config version prepatch --preid beta --no-git-tag-version --no-git-checks
pnpm install
pnpm exec eslint packages/markdownlint-config --max-warnings 0
pnpm exec markdownlint-cli2 --config .markdownlint-cli2.jsonc "packages/markdownlint-config/**/*.md"
pnpm --dir packages/markdownlint-config pack --dry-run
pnpm --dir packages/markdownlint-config publish --access public --tag next --registry https://registry.npmjs.org/ --no-git-checks
pnpm view @zzjtnb/markdownlint-config dist-tags --json --registry https://registry.npmjs.org/
```

测试版本安装与标签纠错属于 npm 通用机制，见[发布常见问题][faq]。

## 发布后核验

### 版本、精确版本与标签

```bash
# 三个包可以独立版本，不要求三个 latest 相同。
pnpm view @zzjtnb/eslint-config version --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config version --registry https://registry.npmjs.org/
pnpm view @zzjtnb/markdownlint-config version --registry https://registry.npmjs.org/

# 检查完整历史与标签，避免只看 latest 漏掉已存在的版本。
pnpm view @zzjtnb/stylelint-config versions dist-tags --json --registry https://registry.npmjs.org/

# 将 2.0.0 替换为本次实际版本，查询那个精确版本，而不是默认标签。
pnpm view @zzjtnb/stylelint-config@2.0.0 version dist.integrity --json --registry https://registry.npmjs.org/
```

### 包元信息

```bash
pnpm view @zzjtnb/eslint-config peerDependencies dependencies engines exports --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/stylelint-config peerDependencies dependencies engines exports --json --registry https://registry.npmjs.org/
pnpm view @zzjtnb/markdownlint-config exports files --json --registry https://registry.npmjs.org/
```

### 在隔离消费项目实际安装

创建新的工作区临时目录，保留旧验证输入和结果，不先清空固定目录。以下方式通过独立 workspace 标记隔离根工作区；如果已有临时验证项目，先核对其状态，不覆盖它。

```bash
# 从仓库根目录执行，创建本轮专用目录。
mkdir -p .tmp/release-consumer
VERIFY_DIR="$(mktemp -d "$PWD/.tmp/release-consumer/run.XXXXXX")"

# 最小 ESM 项目和独立 workspace，防止 add 修改仓库根包。
printf '%s\n' '{"name":"lint-config-consumer-check","private":true,"type":"module"}' > "$VERIFY_DIR/package.json"
printf '%s\n' 'packages: []' > "$VERIFY_DIR/pnpm-workspace.yaml"

# 先把版本替换为本次真实版本；不同包的版本可以不同。
ESLINT_VERSION=2.0.0
STYLELINT_VERSION=2.0.0
MARKDOWNLINT_VERSION=1.0.0
pnpm --dir "$VERIFY_DIR" add -DE eslint "@zzjtnb/eslint-config@$ESLINT_VERSION" stylelint "@zzjtnb/stylelint-config@$STYLELINT_VERSION" markdownlint-cli2 "@zzjtnb/markdownlint-config@$MARKDOWNLINT_VERSION" --registry https://registry.npmjs.org/
```

仅验证一个包时只安装相应主工具和配置包。环境要求以实际安装的版本为准，不用根仓库 Node.js 要求冒充公开包契约。

在 `VERIFY_DIR` 中保存以下三个配置文件；因为最小项目已声明 ESM，这里使用普通 `.js`：

`eslint.config.js`：

```js
import { zzjtnb } from '@zzjtnb/eslint-config'

// 默认开启 TypeScript、Vue 等集成；UnoCSS 需显式开启。
export default zzjtnb()
```

`stylelint.config.js`：

```js
export default {
  extends: ['@zzjtnb/stylelint-config'],
}
```

`.markdownlint-cli2.jsonc`：

```jsonc
{
  "config": {
    "extends": "@zzjtnb/markdownlint-config"
  }
}
```

再创建实际输入，例如 `sample.js`、`sample.css`、`sample.md`；仅空目录运行不能证明配置实际检查了内容。

```bash
pnpm --dir "$VERIFY_DIR" exec eslint sample.js
pnpm --dir "$VERIFY_DIR" exec stylelint sample.css --config stylelint.config.js
pnpm --dir "$VERIFY_DIR" exec markdownlint-cli2 sample.md
```

如需验证 SCSS、Vue、规则覆盖与自动修复，应补充相应输入并检查真实结果；不能只验证模块 import 成功。

## Git 是可选记录，不是发布条件

上面的 version 命令禁用 commit/tag，publish 使用 `--no-git-checks`；这些步骤不会自动推送或创建 GitHub Release。npm 发布完成后，版本和锁文件变化仍在本地，Git 记录由维护者另行决定。

```bash
# 先检查当前分支与暂存范围，不执行任何修改。
git branch --show-current
git status --short
git diff --cached --stat
```

若另外明确决定提交或标记发布，可根据本次实际发布范围执行下面的示例。`2.0.0` 及三包同号仅为示例，独立版本时应采用能明确对应包和版本的记录方式；未改的包不要为凑齐示例而纳入。

```bash
# 仅在确认这些就是本次要提交的范围后执行。
git add packages/eslint-config/package.json packages/stylelint-config/package.json packages/markdownlint-config/package.json pnpm-lock.yaml
git commit -m "chore: record release versions"

# 可选：确认不存在同名标签后创建；不自动推送。
git tag v2.0.0
```

是否推送当前分支、标签或创建 GitHub Release 另行决定，不属于 npm 发布的前提。确认远程、当前分支及要公开的提交和标签都正确后，可分别推送：

```bash
# 先核对远程与当前分支；不沿用其他项目的 master / main 假设。
git remote -v
git branch --show-current

# 仅在确认 origin 和当前分支就是本次目标后执行，不强推。
# HEAD 推送当前分支；分离 HEAD 时先恢复到已确认的目标分支。
git push origin HEAD

# 仅推送本次已核对的标签，不使用 --tags 批量发布其他本地标签。
git push origin refs/tags/v2.0.0
```

如果本次没有创建 `v2.0.0`，不要执行标签示例；独立发版时替换为实际包版本标签。推送失败保留原始错误并核对远程状态，不强推覆盖他人的提交。

## 发布问题与恢复

npm 官方账号权限、查询与发布的 404 区别、版本占用、镜像同步、分发标签、OTP、问题版本弃用及取消发布等，统一见[发布常见问题][faq]；本文不重复维护这些错误正文。本页下节只处理原生命令的目录、参数、构建和恢复问题。

## 原生命令使用问题

### `No workspaces found` 或命令运行到了错误目录

先确认当前位置和 workspace 入口：

```bash
pwd
ls package.json pnpm-workspace.yaml
```

使用 `--dir packages/<目标包>` 执行原生 version / pack / publish。不要在根私有包执行无目标发布，也不要使用没有过滤范围的递归发布；选用交互脚本则另外按[当前发布流程][current]操作。

`pnpm-workspace.yaml` 不仅用于声明工作区，也可能存放普通项目的 pnpm 设置；不能仅因看到这个文件就认定目录或策略有误。

### dry-run 缺少 dist、类型或 JSONC 文件

- ESLint / Stylelint：先重新构建当前源码，核对 `tsdown.config.ts`、`exports`、`files` 与实际产物，再 pack。
- Markdownlint：入口是 `index.jsonc`，不应该要求生成 dist 或执行不存在的 build。
- README、许可证、依赖和元信息也要检查，不能仅因入口文件存在就忽略其他错误。
- 包入口测试使用旧 dist 通过，不代表当前源码已经有可发布产物。

修正前置问题后再次 dry-run，不手工补一个占位 dist，也不改源码别名绕过发布入口。

### 原生命令无法交互读取 OTP

若 pnpm 报 `ERR_PNPM_OTP_NON_INTERACTIVE`，先去掉外层管道、日志捕获或任务转发，在真实终端直接执行目标包目录的 publish。重新发起前仍须核对远程精确版本，不能把客户端退出视为 registry 未接收。npm 的 2FA 要求及验证码错误统一见[发布常见问题][faq]。
